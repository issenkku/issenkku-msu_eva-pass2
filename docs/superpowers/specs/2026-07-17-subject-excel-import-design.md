# แบบออกแบบการนำเข้าข้อมูลรายวิชาด้วย Excel

**วันที่:** 17 กรกฎาคม 2569
**สถานะ:** อนุมัติการออกแบบแล้ว รอตรวจเอกสารก่อนจัดทำ implementation plan

## เป้าหมาย

เพิ่ม workflow สำหรับผู้ดูแลระบบในการเพิ่มและอัปเดตข้อมูลรายวิชาจำนวนมากด้วยไฟล์ Excel โดยผู้ใช้สามารถดาวน์โหลด Template เปล่า หรือส่งออกข้อมูลรายวิชาปัจจุบันมาแก้ไข แล้วอัปโหลดเพื่อตรวจสอบก่อนบันทึกจริง

ระบบต้องแยกรายการใหม่ รายการซ้ำที่เปลี่ยนแปลง และรายการที่ไม่เปลี่ยนแปลงอย่างชัดเจน ผู้ใช้เป็นผู้เลือกรายการซ้ำที่จะอัปเดต ส่วนรายการใหม่จะถูกเพิ่มอัตโนมัติเมื่อยืนยัน การบันทึกต้องเป็นแบบ all-or-nothing เพื่อไม่ให้เกิดข้อมูลเพียงบางส่วน

## ขอบเขต

### อยู่ในขอบเขต

- ดาวน์โหลด Template `.xlsx` เปล่า
- ส่งออกข้อมูลรายวิชาปัจจุบันทั้งหมดเป็น `.xlsx` สำหรับแก้ไขและอัปโหลดกลับ
- อัปโหลดและตรวจ `.xlsx` ไม่เกิน 10 MB และไม่เกิน 5,000 แถวข้อมูล
- Preview รายการใหม่ รายการซ้ำที่เปลี่ยนแปลง รายการไม่เปลี่ยนแปลง และข้อผิดพลาด
- เลือกอัปเดตรายการซ้ำเป็นรายแถว พร้อมเลือกทั้งหมดและไม่เลือกทั้งหมด
- บันทึกข้อมูลใน transaction เดียว
- ป้องกันรหัสรายวิชาซ้ำจาก modal, API, Excel และฐานข้อมูล
- บันทึก audit log ระดับหนึ่งรายการต่อหนึ่งการนำเข้า

### ไม่อยู่ในขอบเขต

- ไฟล์ `.xls` หรือ `.csv`
- การแก้ข้อมูลภายในหน้า Preview
- การนำเข้าสถานะเปิด/ปิดใช้งาน
- การเปลี่ยน `sort_order` จาก Excel
- Background job หรือ staging table สำหรับไฟล์ขนาดใหญ่
- การลบรายวิชาผ่าน Excel
- การเก็บประวัติไฟล์ Excel ต้นฉบับหลังจบการนำเข้า

## ผู้ใช้งานและสิทธิ์

ใช้สิทธิ์เดียวกับหน้าจัดการรายวิชาในปัจจุบัน คือ route อยู่ภายใต้ middleware `auth:sanctum` และ `role:admin` ผู้ใช้ที่ไม่ใช่ admin ต้องเข้าถึง route ดาวน์โหลด อัปโหลด Preview ยืนยัน หรือยกเลิกไม่ได้

## ประสบการณ์ผู้ใช้

### จุดเริ่มต้น

หน้าจัดการรายวิชาเพิ่มปุ่ม `นำเข้าจาก Excel` ข้างปุ่ม `เพิ่มรายวิชา` โดยใช้ `x-button` และรูปแบบ modal ที่มีอยู่ในระบบ

Modal นำเข้าประกอบด้วย:

1. ปุ่ม `ดาวน์โหลด Template เปล่า`
2. ปุ่ม `ส่งออกข้อมูลรายวิชาปัจจุบัน`
3. Drop zone และ file input ที่รับเฉพาะ `.xlsx`
4. ข้อความกำกับขนาดสูงสุด 10 MB และ 5,000 แถว
5. ปุ่มอัปโหลดเพื่อสร้าง Preview

ใช้ component, spacing, สี, icon, focus behavior และรูปแบบ flash message เดียวกับหน้าจัดการผู้ใช้งานและหน้ารายวิชาที่มีอยู่ ไม่สร้าง visual language ชุดใหม่

### หน้า Preview

หลังอัปโหลดและอ่านไฟล์สำเร็จ ระบบนำผู้ใช้ไปหน้า `ตรวจสอบก่อนนำเข้า` แยกจาก modal เพื่อให้มีพื้นที่เพียงพอสำหรับตาราง

หน้า Preview แสดง summary ของสี่กลุ่ม:

- **เพิ่มใหม่:** ไม่พบ `code` ในฐานข้อมูล และจะถูกเพิ่มอัตโนมัติเมื่อยืนยัน
- **ข้อมูลซ้ำที่เปลี่ยนแปลง:** พบ `code` เดิมแต่ข้อมูลต่างกัน เริ่มต้นโดยไม่เลือกอัปเดต
- **ไม่เปลี่ยนแปลง:** พบ `code` เดิมและข้อมูลทุกฟิลด์เหมือนกัน ไม่สามารถเลือกอัปเดต
- **ข้อผิดพลาด:** แถวหรือไฟล์ไม่ผ่าน validation ปุ่มยืนยันต้อง disabled

กลุ่มข้อมูลซ้ำที่เปลี่ยนแปลงมี checkbox รายแถวและปุ่ม `เลือกทั้งหมด` / `ไม่เลือกทั้งหมด` แต่ละแถวแสดงเฉพาะฟิลด์ที่เปลี่ยนในรูปแบบ `ค่าเดิม → ค่าใหม่` พร้อม highlight ความต่าง

Preview เป็น read-only ยกเว้น checkbox เลือกอัปเดต หากข้อมูลผิด ผู้ใช้ต้องแก้ไฟล์ Excel แล้วอัปโหลดใหม่

### ผลลัพธ์หลังยืนยัน

เมื่อบันทึกสำเร็จ ระบบกลับหน้ารายวิชาและแสดงสรุป:

- จำนวนและรหัสที่เพิ่มใหม่
- จำนวนและรหัสที่อัปเดต
- จำนวนและรหัสที่ข้ามเพราะผู้ใช้ไม่เลือกอัปเดต
- จำนวนและรหัสที่ไม่เปลี่ยนแปลง

## รูปแบบไฟล์ Excel

### ชีต

Template มีสองชีต:

1. `ข้อมูลรายวิชา` สำหรับกรอกข้อมูลจริง โดยไม่มีแถวตัวอย่าง
2. `คำแนะนำ` อธิบายคอลัมน์ ค่าที่บังคับ ตัวอย่าง และกติกาการตรวจข้อมูล

ไฟล์ส่งออกข้อมูลปัจจุบันใช้โครงสร้างเดียวกัน แต่เติมรายวิชาทั้งหมดในชีต `ข้อมูลรายวิชา` โดยไม่สนคำค้นหา ตัวกรอง หรือหน้าปัจจุบัน

### คอลัมน์

ชีต `ข้อมูลรายวิชา` ต้องมีหัวคอลัมน์ภาษาไทยตามลำดับนี้:

1. `รหัสรายวิชา`
2. `ชื่อรายวิชา (ไทย)`
3. `ชื่อรายวิชา (อังกฤษ)`
4. `หน่วยกิตรวม`
5. `หน่วยกิตบรรยาย`
6. `หน่วยกิตปฏิบัติ`
7. `หน่วยกิตศึกษาด้วยตนเอง`

ระบบปฏิเสธไฟล์ที่ขาดหัวคอลัมน์ หัวคอลัมน์ซ้ำ มีหัวคอลัมน์อื่นเพิ่ม หรือเรียงลำดับไม่ตรง Template เพื่อป้องกันการจับคู่ข้อมูลผิดช่อง

ไม่ส่งออก `id`, `is_active` หรือ `sort_order`

## การ Normalize และ Validation

### รหัสรายวิชา

- `code` เป็น business identifier ของรายวิชา
- ตัดช่องว่างหัวท้าย และแปลงอักษรอังกฤษเป็นตัวพิมพ์ใหญ่ด้วย Unicode-aware uppercase ก่อนตรวจและบันทึก
- อักษรไทย ตัวเลข เครื่องหมาย และช่องว่างภายในยังคงเดิม
- ต้องมีค่าและยาวไม่เกิน 255 ตัวอักษร
- ตรวจซ้ำโดยใช้ค่าที่ normalize แล้ว

กติกานี้ใช้กับการสร้างและแก้ไขทุกช่องทาง ไม่เฉพาะ Excel

### ชื่อรายวิชา

- ตัดช่องว่างหัวท้าย
- `name_th` บังคับกรอกและยาวไม่เกิน 255 ตัวอักษร
- `name_en` ไม่บังคับและยาวไม่เกิน 255 ตัวอักษร
- ไม่มีการจำกัดชุดภาษา ทั้งสองช่องรองรับ Unicode
- `name_en` ที่ว่างหรือมีแต่ช่องว่างแปลงเป็น `null` และหมายถึงล้างค่าเดิมเมื่ออัปเดต

### หน่วยกิต

- ทั้งสี่คอลัมน์บังคับกรอก
- ต้องเป็นจำนวนเต็มตั้งแต่ศูนย์ขึ้นไป
- ต้องเป็นจริงตามสมการ:

  `หน่วยกิตรวม = หน่วยกิตบรรยาย + หน่วยกิตปฏิบัติ + หน่วยกิตศึกษาด้วยตนเอง`

- ช่องว่าง ค่าทศนิยม ค่าติดลบ และข้อความถือเป็นข้อผิดพลาด

### Formula และเซลล์พิเศษ

เซลล์ข้อมูลที่มีชนิดเป็น Excel Formula ถือเป็นข้อผิดพลาด แม้จะมี cached result ผู้ใช้ต้องใส่ค่าคงที่เพื่อให้ Preview และผลบันทึกแน่นอน

ตอนส่งออก ค่า string ต้องถูกเขียนเป็น string อย่างชัดเจน เพื่อไม่ให้ค่าที่ขึ้นต้นด้วย `=`, `+`, `-` หรือ `@` ถูก Excel ตีความเป็น formula

### จำนวนแถว

นับเฉพาะแถวข้อมูลที่ไม่ว่างทั้งหมด ไม่นับหัวตาราง แถวว่างท้ายชีต หรือชีต `คำแนะนำ` หากเกิน 5,000 แถวให้ปฏิเสธไฟล์ก่อนสร้าง Preview

## นิยามข้อมูลซ้ำ

### ซ้ำภายในไฟล์เดียวกัน

หาก `code` หลัง normalize ซ้ำกันมากกว่าหนึ่งแถว ไฟล์ทั้งหมดไม่ผ่าน validation ระบบแสดงรหัสและเลขแถว Excel ทุกแถวที่เกี่ยวข้อง เช่น `CS101: แถว 2, 8, 12`

ระบบไม่เลือกแถวแรกหรือแถวสุดท้ายแทนผู้ใช้

### ซ้ำกับฐานข้อมูล

- พบ `code` และทุกฟิลด์ที่นำเข้าเหมือนข้อมูลเดิม: จัดเป็น `ไม่เปลี่ยนแปลง`
- พบ `code` แต่มีอย่างน้อยหนึ่งฟิลด์ต่าง: จัดเป็น `ข้อมูลซ้ำที่เปลี่ยนแปลง`
- ไม่พบ `code`: จัดเป็น `เพิ่มใหม่`

ฟิลด์ที่ใช้เปรียบเทียบคือ `name_th`, `name_en`, `credits`, `lecture_credits`, `lab_credits` และ `self_study_credits` ไม่เปรียบเทียบ `is_active` หรือ `sort_order`

## พฤติกรรมการเพิ่มและอัปเดต

### รายการใหม่

- เพิ่มทุกรายการเมื่อผู้ใช้ยืนยัน Preview ที่ไม่มีข้อผิดพลาด
- กำหนด `is_active = true`
- กำหนด `sort_order` ต่อจากค่าสูงสุดปัจจุบันตามลำดับแถวในไฟล์

### รายการซ้ำที่เปลี่ยนแปลง

- checkbox เริ่มต้นเป็นไม่เลือก
- อัปเดตเฉพาะรายการที่ผู้ใช้เลือก
- แทนที่ `name_th`, `name_en` และหน่วยกิตทั้งสี่ช่องด้วยค่าจากไฟล์
- คง `code`, `is_active` และ `sort_order` ของข้อมูลเดิม
- รายการที่ไม่เลือกจัดเป็น `ข้าม`

### รายการไม่เปลี่ยนแปลง

ไม่ออกคำสั่ง update และไม่สามารถเลือกอัปเดต

## Architecture

### Controller และ Route

แยก workflow นำเข้าออกจาก CRUD ใน `SubjectController` เพื่อไม่ให้ controller เดิมรับหลายความรับผิดชอบเกินไป Route ใหม่ยังอยู่ใต้ prefix `subjects` และ middleware admin เดิม โดยมีความสามารถดังนี้:

| Method | URI | Route name | Controller action |
| --- | --- | --- | --- |
| GET | `/subjects/import/template` | `subjects.import.template` | `SubjectImportController@template` |
| GET | `/subjects/import/export` | `subjects.import.export` | `SubjectImportController@export` |
| POST | `/subjects/import/preview` | `subjects.import.preview.store` | `SubjectImportController@storePreview` |
| GET | `/subject-imports/{token}` | `subjects.import.preview.show` | `SubjectImportController@showPreview` |
| POST | `/subject-imports/{token}/confirm` | `subjects.import.confirm` | `SubjectImportController@confirm` |
| DELETE | `/subject-imports/{token}` | `subjects.import.cancel` | `SubjectImportController@cancel` |

Static import routes ต้องประกาศก่อน route `/subjects/{id}` ส่วน route ที่ใช้ token แยก prefix เป็น `/subject-imports` เพื่อไม่ให้ชนกับ subject ID

### Service Boundaries

แยกหน่วยงานภายในอย่างน้อยดังนี้:

- **`SubjectWorkbookFactory`:** สร้าง workbook, styling, คำแนะนำ และข้อมูลส่งออก
- **`SubjectWorkbookReader`:** ตรวจชนิดไฟล์ ชีต หัวคอลัมน์ จำนวนแถว formula และแปลงแถวเป็นค่าดิบ
- **`SubjectImportRowValidator`:** normalize และตรวจ field-level rules โดยไม่ติดต่อฐานข้อมูล
- **`SubjectImportPreviewService`:** โหลดรายวิชาแบบ batch แล้วจัดกลุ่ม new, changed, unchanged และ errors
- **`SubjectImportCommitter`:** ตรวจ snapshot ใหม่อีกครั้งและเขียนฐานข้อมูลใน transaction

แต่ละหน่วยต้องมี input/output ที่ทดสอบแยกได้ ไม่ผูก logic การ parse Excel เข้ากับ Blade หรือ controller

### Preview Snapshot

หลัง parse สำเร็จ ระบบลบไฟล์อัปโหลดดิบและเก็บ parsed snapshot ฝั่งเซิร์ฟเวอร์ใน Laravel cache ด้วย token สุ่มที่คาดเดาไม่ได้

Snapshot ประกอบด้วย:

- user ID ของผู้สร้าง
- ชื่อไฟล์เดิมที่ผ่านการ sanitize
- เวลาสร้างและเวลาหมดอายุ
- normalized rows และเลขแถวต้นทาง
- การจัดกลุ่ม Preview
- fingerprint ของรายวิชาเดิมที่เกี่ยวข้อง

ไม่เก็บ payload ทั้งหมดใน browser หรือ session token ฝั่ง client มีเพียง opaque preview token และรายการ code ที่ผู้ใช้เลือกอัปเดต

Snapshot หมดอายุ 30 นาที และถูกลบทันทีเมื่อยืนยันสำเร็จหรือยกเลิก Token ของผู้ใช้อื่น token ที่หมดอายุ หรือ token ที่ถูกใช้แล้วต้องตอบกลับแบบไม่เปิดเผยข้อมูลภายใน

### Result Summary

รายการ code อาจมีได้ถึง 5,000 ค่า จึงไม่เก็บ summary ทั้งหมดใน flash session หลัง commit ระบบเก็บ result summary ใน cache แยกต่างหากเป็นเวลา 10 นาทีด้วย result token ที่ผูกกับผู้ยืนยัน แล้ว flash เฉพาะ token ขนาดเล็กกลับหน้ารายวิชา

หน้ารายวิชาอ่าน result token หนึ่งครั้ง แสดงจำนวนและรายการ code แบบพับ/ขยายได้ แล้วลบ result cache ค่า flash message ทั่วไปยังใช้ component เดิม

## ขั้นตอนการทำงาน

### สร้าง Preview

1. ตรวจ authentication, role, MIME/extension และขนาด 10 MB
2. เปิด workbook และตรวจว่ามีชีต `ข้อมูลรายวิชา`
3. ตรวจหัวคอลัมน์และจำนวนแถว
4. ตรวจ formula, normalize และ validate ทุกแถว
5. ตรวจ code ซ้ำภายในไฟล์
6. หากมีข้อผิดพลาดระดับแถว สร้างผลตรวจที่ไม่มีสิทธิ์ยืนยันและแสดงข้อผิดพลาดทั้งหมดในครั้งเดียว
7. หากไม่มีข้อผิดพลาด โหลดรายวิชาที่มี code เกี่ยวข้องด้วย query แบบ batch
8. จัดกลุ่มรายการและสร้าง fingerprint ของสถานะฐานข้อมูลที่ใช้ทำ Preview
9. เก็บ snapshot 30 นาทีและ redirect ไปหน้า Preview

### ยืนยัน Preview

1. ตรวจ token, owner, expiry และสถานะ unused
2. ตรวจว่า snapshot ไม่มี validation error และรหัสที่เลือกอัปเดตเป็น subset ของกลุ่ม changed ใน snapshot
3. ใช้ cache lock แล้ว Claim token แบบ atomic เพื่อป้องกันการกดยืนยันซ้ำ หลังขั้นตอนนี้ token ถือว่าถูกใช้แล้วไม่ว่าผล commit จะสำเร็จหรือไม่
4. โหลดข้อมูลปัจจุบันแบบ batch
5. เปรียบเทียบ fingerprint ของรายการเดิม และยืนยันว่า code ของรายการใหม่ยังไม่ถูกสร้าง
6. หากข้อมูลใดเปลี่ยนหลัง Preview ให้หยุดทั้งชุด ไม่เขียนฐานข้อมูล และแจ้งให้สร้าง Preview ใหม่
7. ตรวจ validation และ uniqueness อีกครั้ง
8. เริ่ม database transaction
9. เพิ่มรายการใหม่ตามลำดับไฟล์
10. อัปเดตเฉพาะรายการ changed ที่ผู้ใช้เลือก
11. บันทึก audit log สรุปหนึ่งรายการ
12. commit transaction
13. สร้าง result summary อายุ 10 นาที ลบ Preview snapshot และ redirect กลับหน้ารายวิชาโดย flash เฉพาะ result token

หากเกิด unique constraint violation หรือข้อผิดพลาดระหว่าง transaction ต้อง rollback ทั้งชุดและลบ Preview snapshot เนื่องจาก token ถูกใช้แล้ว UI ต้องแจ้งให้ผู้ใช้สร้าง Preview ใหม่

## Concurrency และ Uniqueness

Fingerprint ของรายวิชาเดิมต้องครอบคลุม ID, normalized code, ฟิลด์ที่เปรียบเทียบ, `is_active`, `sort_order` และ `updated_at` เพื่อให้ตรวจพบการแก้ไขระหว่าง Preview กับ Confirm

เพิ่ม unique constraint ที่ `subjects.code` หลัง normalize ข้อมูลเดิม และเพิ่ม application validation ใน `StoreSubjectRequest` กับ `UpdateSubjectRequest` การ update ต้อง ignore ID ของรายการปัจจุบัน

ฐานข้อมูลจริงได้รับการลบข้อมูลซ้ำเดิมแล้ว หาก migration พบ collision หลัง normalize ให้หยุด migration พร้อมข้อความที่ระบุว่าต้องแก้ code ซ้ำก่อน ไม่เลือกข้อมูลใดทิ้งอัตโนมัติ

## Error Handling

### ข้อผิดพลาดระดับไฟล์

ตัวอย่าง: extension/MIME ไม่ถูกต้อง ไฟล์เสีย เปิด workbook ไม่ได้ ชีตหาย หัวคอลัมน์ผิด หรือขนาดเกิน ข้อผิดพลาดกลุ่มนี้แสดงใน modal และไม่สร้าง Preview

### ข้อผิดพลาดระดับแถว

แสดงในหน้า Preview โดยระบุ:

- เลขแถว Excel
- รหัสรายวิชา ถ้าอ่านได้
- คอลัมน์
- ค่าที่พบในรูปแบบปลอดภัย
- สาเหตุ

รวบรวมข้อผิดพลาดทุกแถวในรอบเดียวเพื่อให้ผู้ใช้แก้ไฟล์ครั้งเดียว ปุ่มยืนยัน disabled หากมีข้อผิดพลาดอย่างน้อยหนึ่งรายการ

### Preview หมดอายุหรือเปลี่ยนแปลง

แจ้งด้วยภาษาที่ผู้ใช้เข้าใจได้ว่า Preview หมดอายุหรือข้อมูลถูกเปลี่ยนหลังการตรวจ และให้กลับไปอัปโหลดใหม่ ไม่แสดง exception, cache key หรือข้อมูลระบบภายใน

## Audit Log

สร้าง audit log หนึ่งรายการเมื่อ transaction สำเร็จ โดยใช้ `AuditLog::record()` และผูก causer เป็น admin ที่ยืนยัน

Properties อย่างน้อยประกอบด้วย:

- ชื่อไฟล์เดิมที่ sanitize แล้ว
- preview token identifier ที่ hash แล้ว ไม่เก็บ token จริง
- จำนวนและรายการ code ที่เพิ่มใหม่
- จำนวนและรายการ code ที่อัปเดต
- จำนวนและรายการ code ที่ข้าม
- จำนวนและรายการ code ที่ไม่เปลี่ยนแปลง

ไม่สร้าง audit log หาก validation ไม่ผ่าน Preview หมดอายุ เกิด concurrency conflict หรือ transaction rollback

## ความปลอดภัยและความเป็นส่วนตัว

- ตรวจสิทธิ์ทุก route ไม่พึ่งการซ่อนปุ่มใน UI
- Token เป็น random opaque value ผูก owner และมีอายุจำกัด
- ไม่เชื่อข้อมูลแถวหรือค่าฟิลด์ที่ส่งกลับจาก browser
- Escape ค่าใน Blade ทุกจุดและ sanitize ชื่อไฟล์ก่อนแสดงหรือบันทึก log
- ไม่เก็บไฟล์ต้นฉบับหลัง parse
- Export ค่า user-controlled เป็น explicit string เพื่อป้องกัน spreadsheet formula injection
- จำกัดขนาดและจำนวนแถวก่อนสร้าง payload ขนาดใหญ่

## Testing Strategy

### Unit Tests

- normalize code: trim, uppercase และ Unicode
- normalize ชื่อและแปลง `name_en` ว่างเป็น `null`
- validation ข้อความ ความยาว จำนวนเต็ม ค่าติดลบ และสมการหน่วยกิต
- ตรวจ formula cell
- duplicate code ภายในไฟล์พร้อมเลขแถวทั้งหมด
- diff เฉพาะฟิลด์ที่เปลี่ยน
- fingerprint และ stale snapshot detection

### Feature Tests

- admin ดาวน์โหลด Template สองชีตพร้อมหัวคอลัมน์ถูกต้อง
- admin ส่งออกข้อมูลรายวิชาทั้งหมดโดยไม่สนตัวกรองหน้าเว็บ
- non-admin เข้า route ใหม่ไม่ได้
- ปฏิเสธชนิดไฟล์ ขนาด ชีต และหัวคอลัมน์ที่ผิด
- ปฏิเสธไฟล์เกิน 5,000 แถว
- Preview แยก new, changed, unchanged และ errors ถูกต้อง
- code ซ้ำแบบต่างตัวพิมพ์หรือมีช่องว่างถูกจัดเป็นรายการเดียวกัน
- changed rows เริ่มต้นไม่ถูกเลือก และ bulk select ส่งเฉพาะ code ที่อนุญาต
- invalid row ทำให้ยืนยันไม่ได้และไม่มี database write
- confirm เพิ่ม new rows และอัปเดตเฉพาะ changed rows ที่เลือก
- unselected changed rows และ unchanged rows ไม่ถูก update
- new rows เปิดใช้งานและต่อ `sort_order` ตามลำดับไฟล์
- transaction rollback เมื่อแถวใดแถวหนึ่งล้มเหลว
- token owner, expiry, reuse และ cancel behavior
- stale Preview และ concurrent insert ทำให้ทั้งชุดไม่ถูกเขียน
- audit log ถูกสร้างเฉพาะ import ที่สำเร็จและมี summary ถูกต้อง
- manual create/update และ API ใช้ normalization กับ uniqueness เดียวกัน

### UI และ Accessibility Tests

- ปุ่มและ modal ใช้ data hooks ไม่มี inline event handler
- drop zone ใช้งานผ่าน keyboard ได้และมี label ที่สัมพันธ์กับ input
- modal จัดการ focus, Escape และ focus return ตาม pattern เดิม
- checkbox มี accessible name ที่ระบุ code
- สถานะ error และ summary ไม่สื่อความหมายด้วยสีอย่างเดียว
- ปุ่มยืนยัน disabled และอธิบายสาเหตุเมื่อมี errors

## Acceptance Criteria

1. Admin ดาวน์โหลด Template เปล่าและไฟล์ข้อมูลปัจจุบันทั้งหมดได้
2. ระบบรับเฉพาะ `.xlsx` ไม่เกิน 10 MB และ 5,000 แถว
3. ไฟล์ผิดหรือมีแถวผิดไม่เขียนฐานข้อมูลแม้แต่รายการเดียว
4. code ถูก normalize และไม่ซ้ำทุกช่องทาง
5. code ซ้ำภายในไฟล์แสดงรหัสและเลขแถวทั้งหมด
6. Preview แสดง new, changed, unchanged และ errors อย่างถูกต้อง
7. ผู้ใช้เลือกอัปเดต changed rows เป็นรายแถวได้ โดยค่าเริ่มต้นคือไม่เลือก
8. diff แสดงเฉพาะค่าที่เปลี่ยนในรูปแบบค่าเดิมไปค่าใหม่
9. confirm เพิ่มรายการใหม่ทั้งหมด อัปเดตเฉพาะรายการที่เลือก และคงสถานะกับลำดับของรายการเดิม
10. การบันทึกเป็น transaction เดียวและ rollback ทั้งหมดเมื่อเกิดข้อผิดพลาดหรือข้อมูลเปลี่ยนหลัง Preview
11. Preview token ปลอดภัย ผูก owner หมดอายุ 30 นาที และใช้ซ้ำไม่ได้
12. หลังสำเร็จ หน้ารายวิชาแสดงผลสรุปครบโดยไม่ส่งรายการหลายพันค่าผ่าน session และมี audit log หนึ่งรายการ
