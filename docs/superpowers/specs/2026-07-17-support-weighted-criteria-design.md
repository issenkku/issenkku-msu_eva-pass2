# เกณฑ์สายสนับสนุนแบบถ่วงน้ำหนัก

วันที่: 17 กรกฎาคม 2569

## เป้าหมาย

เพิ่มประเภทเกณฑ์เฉพาะสำหรับกลุ่มสนับสนุนในหน้า “สร้างเกณฑ์การประเมินใหม่” โดยนำโครงสร้างคะแนนด้านปริมาณและระบบ Workload ที่มีอยู่กลับมาใช้ภายใน ผู้ดูแลเลือกได้ว่าแต่ละเกณฑ์จะรับคะแนนดิบจากผู้ประเมิน หรือคำนวณจากข้อมูล Workload แล้วระบบจึงถ่วงคะแนนตามน้ำหนัก

สูตรมาตรฐานของเกณฑ์ประเภทนี้คือ:

```text
คะแนนถ่วงน้ำหนัก = น้ำหนัก × คะแนนดิบ / 100
```

คะแนนดิบเริ่มต้นอยู่ในช่วง 0–5 และกำหนดค่าสูงสุดแยกต่อเกณฑ์ได้

## ขอบเขต

งานนี้ครอบคลุม:

- ตัวเลือกประเภทเกณฑ์ “เกณฑ์สายสนับสนุน” ในหน้าสร้างและแก้ไขโครงเกณฑ์
- การเลือกแหล่งคะแนนต่อเกณฑ์ระหว่างผู้ประเมินกรอกเองกับ Workload
- การเก็บน้ำหนัก เพดานคะแนนดิบ คำอธิบายเกณฑ์ และข้อกำหนดหลักฐาน
- การคำนวณและแสดงคะแนนถ่วงน้ำหนักอย่างสอดคล้องในทุกบทบาท
- การเชื่อมรายการที่ใช้ Workload เข้ากับหน้าตั้งค่า Workload เดิม
- ความเข้ากันได้กับเกณฑ์ปริมาณและคุณภาพที่มีอยู่

งานนี้ไม่ครอบคลุม:

- การสร้างตารางเกณฑ์สายสนับสนุนชุดใหม่แยกจากโครงเดิม
- การย้ายหรือแปลงข้อมูลเกณฑ์ปี 2568
- การฝังตัวสร้าง Workload ทั้งหมดไว้ในหน้าสร้างโครงเกณฑ์
- การแก้สูตรของเกณฑ์รุ่นที่เริ่มมีการประเมินแล้ว

## ประสบการณ์ผู้ดูแลระบบ

### การเลือกประเภทการประเมิน

ช่อง “ประเภทการประเมิน” ยังคงมีตัวเลือกกลุ่มวิชาการ กลุ่มสนับสนุน และกลุ่มบริหารตามเดิม

เมื่อเลือก “กลุ่มสนับสนุน” ระบบจะแสดงประเภทเกณฑ์เพิ่มในแต่ละรายการประเมิน:

```text
ประเภทเกณฑ์
○ เกณฑ์ด้านปริมาณ
○ เกณฑ์ด้านคุณภาพ
○ เกณฑ์สายสนับสนุน
```

ประเภททั้งสามเป็นตัวเลือกแบบเลือกได้เพียงหนึ่งประเภทต่อรายการประเมิน เมื่อเปลี่ยนออกจาก “กลุ่มสนับสนุน” ระบบจะซ่อนตัวเลือกสายสนับสนุน หากมีข้อมูลเกณฑ์สายสนับสนุนอยู่แล้ว ระบบต้องเตือนก่อนล้างข้อมูลดังกล่าว

### ฟอร์มเกณฑ์สายสนับสนุน

เมื่อเลือก “เกณฑ์สายสนับสนุน” จะแสดงฟิลด์ต่อไปนี้:

- ชื่อกิจกรรม/โครงการ/งาน
- ตัวชี้วัดหรือเกณฑ์การประเมิน
- น้ำหนัก
- คะแนนดิบสูงสุด ค่าเริ่มต้น 5
- แหล่งคะแนน: “ผู้ประเมินกรอกคะแนน” หรือ “คำนวณจาก Workload”
- คำอธิบายระดับหรือแนวทางให้คะแนน
- กำหนดให้แนบหลักฐานหรือไม่
- กำหนดให้กรอกรายละเอียดผลงานหรือชื่อเรื่องหรือไม่

น้ำหนักต้องมากกว่า 0 คะแนนดิบสูงสุดต้องมากกว่า 0 และผลรวมน้ำหนักของเกณฑ์สายสนับสนุนทั้งหมดในรุ่นเดียวกันต้องเท่ากับ 100 ก่อนบันทึกโครงเกณฑ์

### การตั้งค่า Workload

เมื่อบันทึกโครงเกณฑ์สำเร็จ รายการที่เลือก “คำนวณจาก Workload” จะปรากฏในหน้าจัดการ Workload เดิม ผู้ดูแลจึงกำหนดกลุ่ม รายการ ฟิลด์ ตัวเลือก และ `formula_logic` ต่อจากหน้าดังกล่าว

หน้าสร้างเกณฑ์แสดงสถานะของรายการ Workload ว่า “ยังไม่ได้ตั้งค่าสูตร” หรือ “ตั้งค่าสูตรแล้ว” เมื่อกลับมาแก้ไขโครงเกณฑ์ แต่ไม่ทำสำเนาตัวสร้างสูตรมาไว้ในหน้านี้

## แบบข้อมูล

โครงสร้างหลักยังคงเป็น:

```text
CriteriaVersion
  -> ReportData
  -> Category
    -> EvaluationList
      -> QuantityMainCriteria
        -> QuantitySubCriteria
          -> WorkloadForm
            -> WorkloadEntry
```

เกณฑ์สายสนับสนุนใช้ `QuantityMainCriteria` และ `QuantitySubCriteria` ภายใน เพื่อใช้ความสัมพันธ์กับ Workload และการรวม `score_D` ที่มีอยู่ โดยเพิ่ม metadata ที่บอกความหมายใหม่อย่างชัดเจน ไม่ตีความจากชื่อกลุ่มสนับสนุนเพียงอย่างเดียว

เพิ่มฟิลด์ใน `evaluation_lists`:

- `criteria_mode` string ค่าเริ่มต้น `legacy` และรองรับ `support_weighted`

เพิ่มฟิลด์ใน `quantity_sub_criterias`:

- `score_source` string ค่า `manual` หรือ `workload`
- `raw_score_max` decimal ค่าเริ่มต้น 5
- `require_description` boolean ค่าเริ่มต้น false

ใช้ฟิลด์เดิมดังนี้:

- `score_a` เก็บน้ำหนัก
- `score_b` เก็บตัวหาร 100
- `description` เก็บตัวชี้วัด คำอธิบายระดับ หรือแนวทางให้คะแนน
- `require_evidence` ระบุว่าต้องแนบหลักฐาน
- `quantity_scores.score_C` เก็บคะแนนดิบ
- `quantity_scores.score_D` เก็บคะแนนถ่วงน้ำหนัก
- `quantity_scores.description` เก็บชื่อเรื่องหรือรายละเอียดผลงานของผู้ถูกประเมิน

API ของโครงเกณฑ์ส่งและรับ `criteria_mode`, `score_source`, `raw_score_max` และ `require_description` พร้อมข้อมูลปริมาณเดิม ค่าเริ่มต้นของข้อมูลเก่าต้องคงพฤติกรรมเดิมทั้งหมด

## การคำนวณคะแนน

### คะแนนจากผู้ประเมิน

ผู้ประเมินกรอกคะแนนดิบตั้งแต่ 0 ถึง `raw_score_max` ระบบไม่รับ `score_D` จาก client แต่คำนวณใหม่บน server:

```text
C = คะแนนดิบที่ผู้ประเมินกรอก
D = score_a × C / score_b
```

สำหรับเกณฑ์สายสนับสนุน `score_b` เท่ากับ 100 เสมอ

### คะแนนจาก Workload

แต่ละ Workload entry คำนวณ `calculated_score` ด้วย `WorkloadFormulaEvaluator` ตาม `formula_logic` ของฟอร์ม จากนั้นรวมเป็นคะแนนดิบโดยมีเพดาน:

```text
C = MIN(SUM(calculated_score ของรายการในเกณฑ์), raw_score_max)
D = score_a × C / 100
```

สูตร Workload ใช้ expression เช่น `MIN(count, 5)` หรือ `IF(work_count > 0, 5, 0)` และไม่ใช้รูปแบบ assignment เช่น `D = ...`

การรวมคะแนนดิบและการคำนวณคะแนนถ่วงน้ำหนักต้องอยู่ใน service กลางที่ผู้ถูกประเมิน ผู้ประเมิน ผู้บังคับบัญชา ผู้อำนวยการ หน้าสรุป และ dashboard เรียกใช้ร่วมกัน

### การเปลี่ยนสูตร

ห้ามแก้สูตรหรือน้ำหนักของ CriteriaVersion ที่มีรายงานเริ่มใช้งานแล้ว ผู้ดูแลต้องสร้าง CriteriaVersion ใหม่ หากจำเป็นต้องรองรับการแก้สูตรหลังมีข้อมูล ต้องเป็นงานแยกที่มีการคำนวณ Workload entries และ Quantity scores ใหม่ทั้งชุดพร้อม audit log

## หน้าจอตามบทบาท

### ผู้ถูกประเมิน

โครงหน้า เมนู สถานะ และขั้นตอนส่งแบบประเมินยังเหมือนเดิม แต่ส่วนรายการเกณฑ์สายสนับสนุนใช้ข้อความและฟอร์มเฉพาะ ไม่แสดงหัวข้อ “ด้านปริมาณ” หรือคำศัพท์ A/B/C/D แบบภาระงานเดิม

สำหรับแหล่งคะแนน `manual` ผู้ถูกประเมิน:

- อ่านตัวชี้วัดและแนวทางให้คะแนน
- กรอกชื่อเรื่องหรือรายละเอียดผลงานเมื่อเกณฑ์กำหนด
- แนบหลักฐานเมื่อเกณฑ์กำหนด
- ไม่กรอกคะแนนดิบ

สำหรับแหล่งคะแนน `workload` ผู้ถูกประเมิน:

- เปิดหน้าจัดการข้อมูล Workload จากรายการเกณฑ์
- เพิ่ม แก้ไข หรือลบผลงานตามฟอร์มที่ผู้ดูแลกำหนด
- เห็นคะแนนดิบที่ระบบรวมให้และเพดานคะแนน
- แนบหลักฐานต่อ Workload entry

### ผู้ประเมินและผู้อนุมัติ

ผู้ประเมินเห็นรายละเอียดและหลักฐานของผู้ถูกประเมิน พร้อมข้อมูลต่อไปนี้:

- น้ำหนัก
- คะแนนดิบสูงสุด
- คะแนนดิบแบบกรอกได้เมื่อ `score_source = manual`
- คะแนนดิบแบบอ่านอย่างเดียวเมื่อ `score_source = workload`
- คะแนนถ่วงน้ำหนักที่ระบบคำนวณ
- หมายเหตุและประวัติการแก้ไข

ผู้บังคับบัญชาและผู้อำนวยการใช้กติกาเดียวกันตามสิทธิ์แก้ไขที่มีอยู่ ไม่สร้างสูตรคำนวณแยกตามบทบาท

## Validation และข้อผิดพลาด

- ประเภทสายสนับสนุนเลือกพร้อมปริมาณหรือคุณภาพในรายการเดียวกันไม่ได้
- `score_source` ต้องเป็น `manual` หรือ `workload`
- น้ำหนักและคะแนนดิบสูงสุดต้องเป็นตัวเลขบวก
- คะแนนดิบจากผู้ประเมินต้องไม่เกิน `raw_score_max`
- คะแนนรวม Workload ต้องถูก cap ที่ `raw_score_max` ฝั่ง server
- เกณฑ์ที่กำหนด `require_description` ต้องมีรายละเอียดผลงานก่อนส่ง
- เกณฑ์ที่กำหนด `require_evidence` ต้องมีหลักฐานก่อนส่ง
- รายการ `workload` ที่ยังไม่มี Workload form หรือสูตรต้องไม่สามารถส่งแบบประเมินเป็น Pending ได้ และต้องแจ้งชื่อรายการที่ตั้งค่าไม่ครบ
- ผลรวมน้ำหนักต้องเท่ากับ 100 เมื่อบันทึกโครงเกณฑ์

## ความเข้ากันได้ย้อนหลัง

- `criteria_mode = legacy` ใช้ UI, validation และสูตรเดิม
- migration กำหนดค่าเริ่มต้นให้ข้อมูลเก่า จึงไม่ต้อง backfill รายแถว
- เกณฑ์สายวิชาการ กลุ่มบริหาร และเกณฑ์สายสนับสนุนปี 2568 ต้องให้ผลคะแนนเดิม
- ไม่เปลี่ยน URL หรือขั้นตอน assignment/report ที่ใช้อยู่
- ไม่ผูกการคำนวณกับข้อความ `assessment_type` โดยตรง การแสดงตัวเลือกในหน้าสร้างอาศัย assessment type แต่การประมวลผลอาศัย `criteria_mode`

## การทดสอบ

เพิ่มการทดสอบอย่างน้อยดังนี้:

- หน้า create/edit แสดงประเภทสายสนับสนุนเฉพาะเมื่อเลือกกลุ่มสนับสนุน
- ประเภทปริมาณ คุณภาพ และสายสนับสนุนเลือกพร้อมกันไม่ได้
- payload create/update เก็บและอ่าน metadata สายสนับสนุนครบ
- คะแนน manual ถูกจำกัดตาม `raw_score_max` และคำนวณถ่วงน้ำหนักบน server
- คะแนน Workload หลาย entry ถูกรวมและ cap ก่อนถ่วงน้ำหนัก
- เกณฑ์ที่ต้องมีรายละเอียดหรือหลักฐานส่ง Pending ไม่ได้เมื่อข้อมูลไม่ครบ
- CriteriaVersion ที่มีรายงานแล้วไม่อนุญาตให้เปลี่ยนสูตรหรือน้ำหนัก
- summary, dashboard และทุกบทบาทแสดงคะแนนเดียวกัน
- regression tests ของเกณฑ์ legacy ผ่านโดยผลคะแนนไม่เปลี่ยน

## เกณฑ์สำเร็จ

ผู้ดูแลสร้าง template กลุ่มสนับสนุนที่ผสมเกณฑ์ manual และ Workload ได้จากโครงเกณฑ์รุ่นเดียว ผู้ถูกประเมินบันทึกผลงานและหลักฐานผ่านหน้าที่เหมาะกับแหล่งคะแนน ผู้ประเมินให้คะแนนเฉพาะรายการ manual และทุกหน้าคำนวณคะแนนถ่วงน้ำหนักจากกติกาเดียวกันโดยไม่กระทบเกณฑ์เดิม
