# การกรอกคะแนนเกณฑ์สายสนับสนุนตามลำดับการประเมิน

วันที่: 20 กรกฎาคม 2569

## สถานะและความสัมพันธ์กับสเปกเดิม

เอกสารนี้ขยายขอบเขตจาก [Template เกณฑ์สำหรับสายสนับสนุน](./2026-07-20-support-criteria-template-design.md) ให้รองรับการใช้งาน Template ในรายงานจริง ตั้งแต่ผู้ถูกประเมินกรอกคะแนนจนถึงผู้ประเมินแต่ละ Role ตรวจและแก้ไขตามลำดับของระบบ

ข้อกำหนดในสเปก Template เดิมที่ระบุว่าหน้าผู้ถูกประเมิน การคำนวณคะแนน และการบันทึกคะแนนอยู่นอกขอบเขต ให้ถือว่าถูกแทนที่ด้วยเอกสารนี้เฉพาะส่วนเกณฑ์สายสนับสนุน ส่วนโครงสร้าง Template และพฤติกรรมเกณฑ์ปริมาณกับคุณภาพเดิมยังคงเดิม

## เป้าหมาย

- ให้ผู้ถูกประเมินกรอก `ค่าคะแนนที่ได้` ของแต่ละเกณฑ์สายสนับสนุน
- คำนวณและบันทึกคะแนนถ่วงน้ำหนักตามน้ำหนักที่แอดมินกำหนด
- รองรับหลักฐานแบบลิงก์ โดยแอดมินเลือกบังคับแนบเป็นรายเกณฑ์
- ส่งข้อมูลเข้าสู่ลำดับ ผู้ประเมิน กรรมการ และผู้บริหาร ตาม Flow ปัจจุบัน
- ให้ผู้ตรวจในแต่ละ Role แก้คะแนนได้พร้อมเหตุผลและประวัติการแก้ไข
- ใช้ Comment แยกตาม Role ระดับทั้งแบบประเมินที่ระบบมีอยู่แล้ว

## ขอบเขต

งานนี้ครอบคลุม:

- หน้า Create และ Edit Template สำหรับตั้งค่า `บังคับแนบหลักฐาน` รายเกณฑ์สายสนับสนุน
- หน้าผู้ถูกประเมินสำหรับกรอกคะแนน แนบหลักฐาน บันทึกฉบับร่าง และยืนยันส่ง
- หน้าผู้ประเมิน กรรมการ และผู้บริหารสำหรับตรวจและแก้คะแนนในขั้นของตน
- การคำนวณคะแนนถ่วงน้ำหนัก ผลรวมจริง และผลรวมที่ใช้แสดง
- การบันทึกเหตุผลและประวัติเมื่อคะแนนเดิมถูกแก้
- การแสดงเกณฑ์ คะแนน หลักฐาน ประวัติ และผลรวมในสถานะอ่านอย่างเดียว
- การนำคะแนนสายสนับสนุนที่ใช้แสดงเข้าส่วนสรุปคะแนนเดิม

งานนี้ไม่ครอบคลุม:

- การเพิ่ม Role หรือเปลี่ยนลำดับ Assignment Flow
- การสร้างระบบ Comment ใหม่หรือ Comment รายกิจกรรม
- การอัปโหลดไฟล์หลักฐานโดยตรง หลักฐานยังเป็น URL ตามรูปแบบเดิม
- การเปลี่ยนสูตรหรือพฤติกรรมของเกณฑ์ปริมาณและคุณภาพ
- การเชื่อมเกณฑ์สายสนับสนุนกับ Workload

## บทบาทและสิทธิ์

### ผู้ถูกประเมิน

- กรอกและแก้คะแนนได้ขณะที่รายงานอยู่ในสถานะที่ผู้ถูกประเมินแก้ไขได้ตาม Flow เดิม
- บันทึกฉบับร่างหรือยืนยันส่งได้โดยไม่บังคับให้กรอกคะแนนครบทุกข้อ
- เมื่อส่งแล้วจะเห็นคะแนนและหลักฐานแบบอ่านอย่างเดียว และไม่สามารถย้อนกลับมาแก้ระหว่างที่รายงานอยู่ในขั้นของผู้ตรวจ

### ผู้ประเมิน กรรมการ และผู้บริหาร

- เห็นเกณฑ์ คะแนนที่ผู้ถูกประเมินกรอก คะแนนถ่วงน้ำหนัก หลักฐาน และประวัติ
- แก้ `ค่าคะแนนที่ได้` ได้เฉพาะเมื่อรายงานอยู่ในขั้นที่ Role นั้นแก้ไขได้ตาม Flow เดิม
- หากค่าใหม่ต่างจากค่าที่มีอยู่ ต้องระบุเหตุผลก่อนบันทึก
- หากค่าไม่เปลี่ยน ไม่บังคับเหตุผลและไม่สร้างประวัติซ้ำ
- หลักฐานของผู้ถูกประเมินแสดงเป็นลิงก์อ่านอย่างเดียวสำหรับการตรวจสอบ

### Comment

ใช้ Comment ระดับรายงานที่มีอยู่แล้ว:

- `evaluator_comment` สำหรับผู้ประเมิน
- `director_comment` สำหรับกรรมการ
- `manager_comment` สำหรับผู้บริหาร

ไม่มี Comment เพิ่มในแต่ละเกณฑ์สายสนับสนุน

## UI ฝั่งแอดมิน

ในแต่ละรายการของ `support_criterias` เพิ่ม Checkbox:

```text
☐ บังคับแนบหลักฐาน
```

Checkbox นี้เป็นอิสระในแต่ละรายการ และต้องบันทึก โหลด และแก้ไขกลับมาแสดงค่าเดิมได้

## UI ฝั่งผู้ถูกประเมิน

### จอขนาดใหญ่

ใช้ตารางตามแบบเอกสาร โดยหนึ่งแถวแทนหนึ่งเกณฑ์:

```text
ลำดับ | กิจกรรม/โครงการ/งาน | ตัวชี้วัด/เกณฑ์การประเมิน | ระดับค่าเป้าหมาย
       | น้ำหนัก | ค่าคะแนนที่ได้ | คะแนนถ่วงน้ำหนัก
```

- กิจกรรม ตัวชี้วัด ค่าเป้าหมาย และน้ำหนักเป็นข้อมูลอ่านอย่างเดียวจาก Template
- `ค่าคะแนนที่ได้` เป็นช่องตัวเลขที่ผู้ถูกประเมินกรอก
- `คะแนนถ่วงน้ำหนัก` เป็นค่าอ่านอย่างเดียวและอัปเดตทันทีเมื่อคะแนนเปลี่ยน
- แสดงส่วนแนบลิงก์หลักฐานใต้แถวของเกณฑ์ เพิ่มและลบ URL ได้หลายรายการ
- เกณฑ์ที่บังคับหลักฐานต้องมีข้อความและสถานะที่มองเห็นชัดเจน

### จอขนาดเล็ก

เปลี่ยนแต่ละแถวเป็นการ์ด โดยคงข้อมูลและช่องกรอกชุดเดียวกับตาราง ไม่สร้างแบบข้อมูลหรือพฤติกรรมอีกชุดหนึ่ง

### หน้าสรุป

- แสดงผลรวมคะแนนสายสนับสนุนที่ใช้แสดงด้วยทศนิยม 2 ตำแหน่ง
- หากผลรวมจริงเกิน 100 ให้แสดง `100.00`
- ไม่แก้หรือลดค่าคะแนนรายข้อเพื่อทำให้ผลรวมเหลือ 100

## คะแนนและสูตรคำนวณ

`ค่าคะแนนที่ได้` มีข้อกำหนดดังนี้:

- เว้นว่างได้
- ค่าต่ำสุด 0
- ไม่มีค่าสูงสุดใน UI หรือ Validation ระดับธุรกิจ
- รองรับทศนิยมไม่เกิน 2 ตำแหน่ง

คะแนนถ่วงน้ำหนักจริงของแต่ละรายการ:

```text
คะแนนถ่วงน้ำหนักจริง = น้ำหนัก × ค่าคะแนนที่ได้ ÷ 100
```

หากค่าคะแนนว่าง คะแนนถ่วงน้ำหนักของรายการนั้นเป็นค่าว่างและไม่นำมารวม

ผลรวมจริงและผลรวมที่ใช้แสดง:

```text
ผลรวมจริง = ผลรวมคะแนนถ่วงน้ำหนักจริงของเกณฑ์สายสนับสนุนทั้งหมดในรายงาน
ผลรวมที่ใช้แสดง = min(ผลรวมจริง, 100)
```

เพดาน 100 ใช้เฉพาะผลรวมเกณฑ์สายสนับสนุน ไม่เปลี่ยนเพดานหรือสูตรของเกณฑ์ปริมาณและคุณภาพ

ตัวอย่าง: น้ำหนัก 20 และค่าคะแนนที่ได้ 125.50 ให้คะแนนถ่วงน้ำหนักจริง 25.10 หากผลรวมจริงทั้งส่วนเป็น 112.50 ระบบเก็บ 112.50 และแสดง 100.00

## หลักฐาน

- หลักฐานเป็น URL และเพิ่มได้หลายรายการเหมือนระบบเดิม
- แอดมินกำหนด `require_evidence` เป็นราย `SupportCriteria`
- หาก `require_evidence` เป็นจริง ต้องมี URL ที่ไม่ว่างและถูกต้องอย่างน้อยหนึ่งรายการ แม้ค่าคะแนนของเกณฑ์นั้นจะยังว่าง
- กติกาหลักฐานใช้ทั้งการบันทึกฉบับร่างและการยืนยันส่ง
- Client ตรวจเพื่อให้ข้อความตอบกลับรวดเร็ว และ Server ตรวจซ้ำเพื่อป้องกัน payload ที่ไม่ถูกต้อง
- การบันทึกหลักฐานสายสนับสนุนต้องไม่ลบหรือเปลี่ยนหลักฐานของเกณฑ์คุณภาพและ Workload ที่อยู่ในรายงานเดียวกัน

## แบบข้อมูล

### `support_criterias`

เพิ่ม:

- `require_evidence` — boolean ค่าเริ่มต้น false

### `support_scores`

สร้างตารางคะแนนปัจจุบัน โดยมีข้อมูลหลัก:

- `id`
- `report_id` — อ้างอิงรายงานและลบตามรายงาน
- `support_criteria_id` — อ้างอิงเกณฑ์และลบตามเกณฑ์
- `achieved_score` — `decimal(20,2)` และเป็น nullable
- `weighted_score` — คะแนนถ่วงน้ำหนักจริงแบบ `decimal(20,2)` และเป็น nullable
- `modification_reason` — เหตุผลล่าสุด เป็น nullableสำหรับการกรอกครั้งแรก
- `modifier_user_id` — ผู้แก้ไขล่าสุด เป็น nullableและใช้ `nullOnDelete`
- `modifier_role` — Role ผู้แก้ไขล่าสุด เป็น nullable
- timestamps

กำหนด unique key ที่ `(report_id, support_criteria_id)` เพื่อให้หนึ่งรายงานมีคะแนนปัจจุบันหนึ่งรายการต่อเกณฑ์

แม้ข้อกำหนดธุรกิจไม่มีค่าสูงสุด แต่ฐานข้อมูลต้องมีขนาดตัวเลขที่แน่นอน จึงใช้ `decimal(20,2)` และไม่กำหนด `max` ใน UI หรือ Validation

### `support_score_histories`

สร้างตารางประวัติ โดยมีข้อมูลหลัก:

- `report_id`
- `support_criteria_id`
- `previous_achieved_score` — `decimal(20,2)` และเป็น nullable
- `new_achieved_score` — `decimal(20,2)` และเป็น nullable
- `previous_weighted_score` — `decimal(20,2)` และเป็น nullable
- `new_weighted_score` — `decimal(20,2)` และเป็น nullable
- `reason`
- `modifier_user_id`
- `modifier_role`
- timestamps

ประวัติเป็นข้อมูลต่อเนื่องและไม่ถูกลบเมื่อมีการแก้ครั้งถัดไป

### `evidence_answers`

เพิ่ม `support_criteria_id` แบบ nullable และ foreign key ไปยัง `support_criterias` ข้อมูลหลักฐานสายสนับสนุนยังเก็บ `evaluation_list_id` และ `report_id` ตามโครงเดิม เพื่อคงการค้นตามรายการประเมินและรายงาน

### `reports`

เพิ่ม `support_score_total` แบบ `decimal(20,2)` ค่าเริ่มต้น `0.00` เพื่อเก็บผลรวมจริงก่อนจำกัดการแสดงผล โดยไม่เขียนทับ Comment หรือคะแนนของประเภทเดิม

## การรับส่งและบันทึกข้อมูล

Payload คะแนนสายสนับสนุนใช้ array แยกจาก `quantity_list` และ `quality_list` แต่ส่งผ่าน endpoint ของ Role เดิมเพื่อคง Transaction และการเปลี่ยนสถานะไว้จุดเดียวกัน ตัวอย่างโครงสร้าง:

```text
support_list[]:
  support_criteria_id
  achieved_score
  modification_reason
  evidence_links[]
```

Server ต้องดำเนินการดังนี้:

1. ตรวจสิทธิ์ผู้ใช้ รายงาน และสถานะตาม Flow เดิม
2. ตรวจว่า `support_criteria_id` อยู่ใน CriteriaVersion ของรายงานนั้น
3. ตรวจค่าคะแนนและ URL หลักฐาน
4. ตรวจหลักฐานบังคับทุกเกณฑ์ แม้เกณฑ์นั้นไม่มีคะแนน
5. คำนวณ `weighted_score` จากน้ำหนักในฐานข้อมูล ไม่รับค่าคำนวณจาก Browser
6. หากแก้ค่าที่มีอยู่ในขั้นผู้ตรวจ ให้ตรวจเหตุผลและสร้างประวัติ
7. Upsert คะแนนและ Sync เฉพาะหลักฐานสายสนับสนุน
8. คำนวณและเก็บผลรวมจริงของสายสนับสนุน
9. บันทึกคะแนน หลักฐาน ประวัติ ผลรวม Comment และสถานะใน Transaction เดียวกัน

การกรอกครั้งแรกของผู้ถูกประเมินไม่ต้องมีเหตุผล การแก้ไขระหว่างฉบับร่างสามารถเก็บประวัติตามรูปแบบเดิมโดยไม่บังคับเหตุผล ส่วนการเปลี่ยนคะแนนโดยผู้ประเมิน กรรมการ หรือผู้บริหารต้องมีเหตุผล

## การแสดงผลในแต่ละ Role

- หน้าผู้ถูกประเมินโหมดแก้ไข: ช่องคะแนนและหลักฐานตามกติกา
- หน้าผู้ถูกประเมินหลังส่ง: คะแนนและหลักฐานอ่านอย่างเดียว
- หน้าผู้ประเมิน กรรมการ และผู้บริหารในขั้นที่แก้ได้: ช่องคะแนน เหตุผล และ Comment ของ Role
- หน้าของ Role ที่ยังไม่ถึงขั้นหรือผ่านขั้นแล้ว: อ่านอย่างเดียว
- ทุกหน้าที่เกี่ยวข้องแสดงคะแนนถ่วงน้ำหนัก ผลรวมที่ใช้แสดง และประวัติด้วยรูปแบบเดียวกัน

## ข้อผิดพลาดและข้อความแจ้งเตือน

- คะแนนติดลบหรือมีทศนิยมเกิน 2 ตำแหน่ง: ปฏิเสธและระบุเกณฑ์ที่ผิด
- URL หลักฐานไม่ถูกต้อง: ปฏิเสธและระบุเกณฑ์ที่ผิด
- ขาดหลักฐานบังคับ: ปฏิเสธทั้ง Draft และ Submit พร้อมชื่อกิจกรรม
- ผู้ตรวจเปลี่ยนคะแนนโดยไม่ให้เหตุผล: ปฏิเสธและระบุเกณฑ์ที่ต้องใส่เหตุผล
- เกณฑ์ไม่อยู่ในรายงานหรือ Role ไม่มีสิทธิ์แก้: ปฏิเสธโดยไม่แก้ข้อมูล
- หาก Transaction ล้มเหลว คะแนน หลักฐาน ประวัติ ผลรวม Comment และสถานะต้องไม่เปลี่ยนบางส่วน

## การทดสอบ

### Template

- Create และ Edit บันทึก โหลด และยกเลิก `require_evidence` รายเกณฑ์ได้
- การตั้งค่าหลักฐานของเกณฑ์สายสนับสนุนไม่กระทบปริมาณและคุณภาพ

### ผู้ถูกประเมิน

- แสดงรายการสายสนับสนุนครบตามลำดับและตอบสนองต่อขนาดหน้าจอ
- บันทึกคะแนนว่าง ค่า 0 ค่ามากกว่า 100 และทศนิยม 2 ตำแหน่งได้
- ปฏิเสธค่าติดลบและทศนิยมเกิน 2 ตำแหน่ง
- คำนวณและบันทึกคะแนนถ่วงน้ำหนักจริงจากน้ำหนักในฐานข้อมูล
- บันทึกและส่งได้โดยคะแนนไม่ครบ
- ปฏิเสธทั้ง Draft และ Submit เมื่อขาดหลักฐานบังคับ
- บันทึก URL หลายรายการและไม่ลบหลักฐานประเภทอื่น
- หลังส่งไม่สามารถแก้คะแนนจากหน้าผู้ถูกประเมิน

### ผู้ตรวจแต่ละ Role

- ผู้ประเมิน กรรมการ และผู้บริหารแก้คะแนนได้เฉพาะขั้นของตน
- การเปลี่ยนคะแนนต้องมีเหตุผล
- การไม่เปลี่ยนคะแนนไม่สร้างประวัติซ้ำ
- ประวัติเก็บค่าเดิม ค่าใหม่ คะแนนถ่วงน้ำหนักเดิมและใหม่ เหตุผล ผู้แก้ Role และเวลา
- Comment ของแต่ละ Role ยังบันทึกและแสดงตามพฤติกรรมเดิม

### ผลรวมและ Regression

- ผลรวมจริงเกิน 100 ถูกเก็บตามจริง แต่ทุก UI แสดงสูงสุด 100
- เพดานนี้ใช้เฉพาะส่วนสายสนับสนุน
- คะแนนที่ใช้แสดงเข้าส่วนสรุปคะแนนเดิมอย่างถูกต้อง
- Full suite ของเกณฑ์ปริมาณ คุณภาพ Workload หลักฐาน Comment และ Assignment Flow ต้องผ่าน

## เกณฑ์สำเร็จ

ผู้ถูกประเมินสามารถกรอกคะแนนสายสนับสนุนและแนบหลักฐานตามที่แอดมินกำหนด บันทึกหรือส่งตาม Flow เดิมได้โดยไม่บังคับกรอกคะแนนครบ ผู้ตรวจในแต่ละ Role สามารถแก้คะแนนในขั้นของตนพร้อมเหตุผลและประวัติ ผลรวมจริงถูกเก็บครบและผลรวมสายสนับสนุนที่แสดงไม่เกิน 100 โดยไม่กระทบเกณฑ์ Comment หลักฐาน และลำดับการประเมินเดิม
