# Support Indicator Grouped Projects Design

วันที่: 2026-07-21
สถานะ: อนุมัติแนวทางแล้ว รอตรวจทานเอกสารก่อนพัฒนา

## ปัญหา

เกณฑ์สายสนับสนุนปัจจุบันเก็บ `ตัวชี้วัด/เกณฑ์การประเมิน` เป็น Rich Text ก้อนเดียว เช่น 2.1, 2.2, 2.3 และ 2.4 รวมอยู่ในช่องเดียว ขณะที่กิจกรรมหรือโครงการของผู้ถูกประเมินเป็นรายการภายใต้เกณฑ์หลักโดยไม่มีความสัมพันธ์กับข้อย่อย ระบบจึงไม่สามารถแสดงหรือตรวจได้ว่าแต่ละโครงการสังกัดข้อ 2.1 หรือ 2.2

## เป้าหมาย

- ให้ Admin กำหนดตัวชี้วัดย่อยแบบมีโครงสร้างภายใต้เกณฑ์สายสนับสนุน
- ให้ผู้ถูกประเมินเพิ่มหลายโครงการภายใต้ตัวชี้วัดย่อยแต่ละข้อ
- ให้หนึ่งโครงการสังกัดตัวชี้วัดย่อยได้เพียงข้อเดียว
- ไม่กำหนดจำนวนโครงการขั้นต่ำและไม่บล็อกการบันทึกหรือยืนยันส่งเมื่อกลุ่มว่าง
- รักษาคะแนน หลักฐาน Comment เหตุผล ประวัติ และ Flow การประเมินเดิม

## รูปแบบฝั่ง Admin

เพิ่มตัวเลือก `แยกโครงการตามตัวชี้วัดย่อย` ภายในรายการเกณฑ์สายสนับสนุน

- ตัวเลือกนี้ใช้งานได้เมื่อเลือก `อนุญาตให้ผู้ถูกประเมินเพิ่มกิจกรรม/โครงการ` เท่านั้น
- หากเลือกโหมดแบ่งข้อย่อยแล้ว Admin ยกเลิกการอนุญาตเพิ่มกิจกรรม ระบบต้องยกเลิกโหมดแบ่งข้อย่อยด้วยเมื่อยังไม่มีข้อมูลอ้างอิง หรือปฏิเสธการเปลี่ยนเมื่อมีโครงการอ้างอิง

เมื่อไม่เลือก:

- ใช้ช่อง Rich Text `ตัวชี้วัด/เกณฑ์การประเมิน` เดิม
- หากเปิดให้เพิ่มกิจกรรม ผู้ถูกประเมินเพิ่มรายการแบบไม่แบ่งกลุ่มเหมือนระบบปัจจุบัน

เมื่อเลือก:

- ซ่อนและไม่ใช้ช่อง Rich Text `ตัวชี้วัด/เกณฑ์การประเมิน` เดิม
- แสดงรายการตัวชี้วัดย่อยแทน โดยแต่ละรายการมี `รหัสข้อ` เช่น `2.1` และ `รายละเอียดตัวชี้วัด` แบบ Rich Text
- Admin เพิ่ม แก้ไข ลบ และจัดลำดับข้อย่อยได้
- ต้องมีตัวชี้วัดย่อยอย่างน้อยหนึ่งข้อก่อนบันทึก Template
- ตารางประเมินแสดงรายการข้อย่อยตามลำดับแทนข้อความ indicator เดิม จึงไม่มีการกรอกหรือแสดงข้อมูลซ้ำสองชุด

## รูปแบบฝั่งผู้ถูกประเมิน

เมื่อกด `กรอกข้อมูล` หรือ `แก้ไขข้อมูล` ระบบแสดงส่วนกิจกรรมเป็นกลุ่มตามตัวชี้วัดย่อย เช่น:

```text
2.1 มีการดำเนินการวิจัยเพื่อพัฒนางาน/รายงานความก้าวหน้า
    โครงการที่ 1 ...
    โครงการที่ 2 ...
    + เพิ่มโครงการในข้อ 2.1

2.2 มีการเผยแพร่ผลงานวิจัย
    โครงการที่ 1 ...
    + เพิ่มโครงการในข้อ 2.2
```

- การกดเพิ่มภายในกลุ่มกำหนดตัวชี้วัดย่อยให้โครงการอัตโนมัติ
- แต่ละข้อย่อยมีโครงการได้ไม่จำกัด
- ผู้ถูกประเมินแก้ไขหรือลบโครงการของตนเองได้ตาม Flow ปัจจุบัน
- หากเพิ่มโครงการผิดข้อ ผู้ถูกประเมินลบรายการและเพิ่มใหม่ในข้อที่ถูกต้อง
- กลุ่มที่ไม่มีโครงการแสดงสถานะ `ยังไม่มีโครงการ` แต่ไม่ถือเป็นข้อผิดพลาด
- ค่าใน Modal ยังเก็บบนหน้าจอจนกดบันทึกฉบับร่างหรือยืนยันส่งของหน้าหลัก

## รูปแบบฝั่งผู้ประเมิน

- ผู้ประเมิน ผู้อำนวยการ และผู้บริหารเห็นโครงการแยกตามข้อย่อยเดียวกับผู้ถูกประเมิน
- แต่ละ Role แก้ไขข้อความโครงการเดิมได้โดยต้องระบุเหตุผลและเก็บประวัติตามระบบปัจจุบัน
- ผู้ประเมินไม่สามารถเพิ่ม ลบ ย้าย หรือจัดลำดับโครงการ
- Comment ของแต่ละ Role ยังคงทำงานตาม Flow เดิม

## โครงสร้างข้อมูล

เพิ่มตาราง `support_indicator_items` สำหรับนิยามข้อย่อยของ Admin:

- `id`
- `support_criteria_id`
- `sequence`
- `code`
- `description` แบบ Rich Text
- timestamps

เพิ่มคอลัมน์ `group_activity_entries_by_indicator` แบบ boolean ใน `support_criterias` ค่าเริ่มต้นเป็น `false`

ปรับคอลัมน์ `support_criterias.indicator` ให้ nullable:

- เกณฑ์แบบเดิมยังบังคับกรอก `indicator`
- เกณฑ์ที่แบ่งข้อย่อยเก็บ `indicator = null` และใช้ `support_indicator_items` แทน โดยไม่สร้างข้อความ placeholder

เพิ่มคอลัมน์ `support_indicator_item_id` แบบ nullable ใน `support_activity_entries`:

- nullable เพื่อรองรับเกณฑ์และกิจกรรมเดิมที่ไม่แบ่งข้อย่อย
- foreign key อ้างอิง `support_indicator_items`
- โครงการหนึ่งแถวมีค่า foreign key ได้เพียงหนึ่งค่า จึงสังกัดได้ข้อย่อยเดียว
- หลายโครงการอ้างอิงข้อย่อยเดียวกันได้

กำหนด unique constraint ของ `support_indicator_items` ที่ `support_criteria_id + code` เพื่อไม่ให้มีรหัสข้อซ้ำภายในเกณฑ์เดียวกัน

ความสัมพันธ์:

```text
SupportCriteria 1 ── * SupportIndicatorItem
SupportIndicatorItem 1 ── * SupportActivityEntry
SupportCriteria 1 ── * SupportActivityEntry
```

## Validation และความปลอดภัยของข้อมูล

- เมื่อเปิดโหมดแบ่งข้อย่อย ต้องส่งตัวชี้วัดย่อยอย่างน้อยหนึ่งรายการ
- `code` และ Rich Text `description` ของแต่ละข้อเป็นข้อมูลบังคับ
- `code` ต้องไม่ซ้ำกันภายในเกณฑ์เดียวกัน
- ลำดับข้อย่อยต้องเป็นจำนวนเต็มบวกและถูกจัดใหม่หลังเพิ่ม ลบ หรือลากเรียง
- เมื่อบันทึกโครงการในเกณฑ์ที่แบ่งข้อย่อย ต้องมี `support_indicator_item_id`
- Server ต้องตรวจว่าข้อย่อยนั้นเป็นของ `support_criteria_id` และ Criteria Version เดียวกับรายงาน
- ห้ามใช้ ID ของข้อย่อยจากเกณฑ์อื่นหรือส่งโครงการหนึ่งรายการซ้ำในหลายกลุ่ม
- ไม่มี validation จำนวนโครงการขั้นต่ำ
- Admin ลบข้อย่อยหรือปิดโหมดแบ่งข้อย่อยได้เมื่อยังไม่มีโครงการอ้างอิงเท่านั้น หากมีข้อมูลแล้วระบบปฏิเสธพร้อมข้อความอธิบาย
- การปิด checkbox ไม่ลบข้อย่อยหรือโครงการแบบเงียบ ๆ

## Payload และการอ่านข้อมูล

- ฝั่ง Admin ส่ง `indicator_items` เป็นรายการเรียงลำดับภายใต้ `support_criterias` แต่ละรายการ
- ฝั่งประเมินยังส่ง `activity_entries` ภายใต้เกณฑ์หลักเหมือนเดิม แต่แต่ละโครงการในโหมดแบ่งข้อย่อยต้องมี `support_indicator_item_id`
- UI แสดงโครงการแบบแยกกลุ่ม แต่ payload เก็บเป็นรายการเดียวพร้อม foreign key เพื่อลดความซับซ้อนของการเพิ่ม ลบ และจัดลำดับ
- Read model โหลดข้อย่อยตาม `sequence` และโหลดโครงการตาม `support_indicator_item_id` โดยไม่ query ซ้ำต่อแถว
- เมื่อ Reviewer ส่งข้อมูลกลับ Server ต้องยืนยันว่า ID และลำดับโครงการเดิมไม่เปลี่ยน รวมถึง `support_indicator_item_id` ต้องเท่าเดิม

## ความเข้ากันได้กับข้อมูลเดิม

- เกณฑ์เดิมมี `group_activity_entries_by_indicator = false` และทำงานแบบเดิมทันที
- `indicator` เดิมยังคงอยู่ในฐานข้อมูลเพื่อรองรับเกณฑ์ที่ไม่แบ่งข้อย่อย
- เกณฑ์ที่เปิดโหมดแบ่งข้อย่อยใช้ `support_indicator_items` เป็นแหล่งแสดงผล และไม่ใช้ `indicator`
- กิจกรรมเดิมที่ไม่มี `support_indicator_item_id` ยังคงแสดงและแก้ไขได้ในเกณฑ์แบบเดิม
- ไม่มีการแปลง Rich Text เดิมเป็นข้อย่อยอัตโนมัติ เพราะรูปแบบเลขข้อและข้อความไม่สม่ำเสมอ

## สิ่งที่ไม่เปลี่ยน

- คะแนนที่ได้ น้ำหนัก และสูตรคะแนนถ่วงน้ำหนัก
- ผลรวมคะแนนสายสนับสนุนและเพดานแสดงผล 100
- หลักฐานและกติกาบังคับแนบหลักฐานระดับเกณฑ์หลัก
- Comment ของแต่ละ Role
- เหตุผลและประวัติการแก้ไขของผู้ประเมิน
- สถานะรายงาน การบันทึกฉบับร่าง และการยืนยันส่ง
- การ sanitize Rich Text และ Summernote toolbar เดิม

## การทดสอบ

- Admin สร้าง แก้ไข ลบ และจัดลำดับตัวชี้วัดย่อย
- โหมดแบ่งข้อย่อยแทนที่ช่อง indicator เดิมโดยไม่แสดงข้อมูลซ้ำ
- ผู้ถูกประเมินเพิ่มหลายโครงการในข้อย่อยเดียวและต่างข้อย่อยได้
- โครงการหนึ่งรายการมีข้อย่อยได้เพียงข้อเดียว
- Server ปฏิเสธข้อย่อยที่เป็นของเกณฑ์หรือ Criteria Version อื่น
- กลุ่มว่างไม่บล็อกการบันทึกฉบับร่างหรือยืนยันส่ง
- Admin ลบข้อย่อยหรือปิดโหมดไม่ได้เมื่อมีโครงการอ้างอิง
- Reviewer แก้ไขรายการเดิมพร้อมเหตุผลและประวัติ แต่เพิ่ม ลบ ย้าย หรือเรียงไม่ได้
- เกณฑ์และกิจกรรมเดิมที่ไม่แบ่งข้อย่อยยังทำงานเหมือนเดิม
- รัน focused tests, full PHP suite, JavaScript tests, Vite build, Blade cache และ `git diff --check`

## เกณฑ์สำเร็จ

Admin สามารถกำหนดตัวชี้วัดย่อย 2.1, 2.2 และข้ออื่น ๆ เป็นข้อมูลแบบมีโครงสร้าง ผู้ถูกประเมินเพิ่มโครงการหลายรายการภายใต้แต่ละข้อได้โดยโครงการหนึ่งสังกัดได้เพียงข้อเดียว กลุ่มว่างไม่ขัดขวาง Flow และระบบเดิมด้านคะแนน หลักฐาน Comment ประวัติ และการส่งรายงานยังทำงานครบถ้วน
