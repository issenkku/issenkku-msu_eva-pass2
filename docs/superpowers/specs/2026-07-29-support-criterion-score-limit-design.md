# จำกัดคะแนนที่ได้ของเกณฑ์สายสนับสนุน

## เป้าหมาย

จำกัดช่อง `ค่าคะแนนที่ได้` ระดับเกณฑ์สายสนับสนุนให้รับเฉพาะจำนวนเต็ม `1`, `2`, `3`, `4` หรือ `5` และค่าที่กรอกต้องไม่เกิน `ระดับค่าเป้าหมาย` ของเกณฑ์นั้น

ระบบต้องตรวจเงื่อนไขทั้งใน Browser และ Server เพื่อแจ้งข้อผิดพลาดได้รวดเร็วและป้องกันการส่ง request ที่ข้ามข้อจำกัดหน้าเว็บ

## ขอบเขต

การเปลี่ยนแปลงใช้เฉพาะ `support_list[*][achieved_score]` ซึ่งเป็นคะแนนระดับเกณฑ์ตามช่องใน Modal ประเมินสายสนับสนุน

ไม่เปลี่ยนกติกาของ `support_list[*][activity_entries][*][achieved_score]` คะแนนรายกิจกรรม/โครงการยังคงรับค่า `0–100` และทศนิยมไม่เกินสองตำแหน่งตามสเปกเดิม

ช่องคะแนนระดับเกณฑ์ยังคงเป็น nullable ระหว่างการแก้ไข เพื่อรักษา workflow การกรอกและการตรวจความครบถ้วนที่มีอยู่

## กติกาคะแนน

คะแนนระดับเกณฑ์ที่ไม่ว่างต้องผ่านทุกเงื่อนไขต่อไปนี้:

- เป็นจำนวนเต็ม
- มีค่าตั้งแต่ `1` ถึง `5`
- ไม่เกิน `support_criterias.target_value` ของเกณฑ์ที่อ้างถึง

ดังนั้นเพดานที่ Browser แสดงคือค่าต่ำสุดระหว่าง `5` กับ `target_value` ตัวอย่างเช่น เกณฑ์ที่มีเป้าหมาย `3.50` จะรับจำนวนเต็มได้เฉพาะ `1`, `2` หรือ `3`

หากข้อมูลเดิมมี `target_value` ต่ำกว่า `1` จะไม่มีคะแนนที่ไม่ว่างซึ่งผ่านกติกา ผู้ใช้ยังปล่อยช่องว่างได้ แต่ Server จะปฏิเสธคะแนนจำนวนเต็มทุกค่าจนกว่า Admin จะแก้ระดับค่าเป้าหมายให้ไม่น้อยกว่า `1`

ระบบไม่ปรับหรือตัดคะแนนที่ผิดเงื่อนไขให้อัตโนมัติ แต่จะแจ้งข้อผิดพลาดและให้ผู้ใช้แก้ไขเอง เพื่อไม่ให้เกิดการเปลี่ยนคะแนนโดยไม่รู้ตัว

## หน้าจอและการแจ้งข้อผิดพลาด

ช่องคะแนนระดับเกณฑ์ใช้ `type="number"`, `min="1"`, `step="1"` และ `max` เท่ากับเพดานของเกณฑ์ พร้อมส่ง `target_value` ให้ JavaScript ผ่าน data attribute

ใต้ช่องแสดงข้อความกำกับที่ระบุข้อจำกัดและค่าเป้าหมายจริง เช่น:

> กรอกเฉพาะจำนวนเต็ม 1–5 และไม่เกินระดับค่าเป้าหมาย 4

JavaScript ของ Modal ตรวจค่าก่อนปิดหรือยืนยัน Modal หากค่าไม่เป็นจำนวนเต็ม อยู่นอกช่วง `1–5` หรือเกินเป้าหมาย ให้แสดงข้อความที่ระบุชื่อเกณฑ์และค่าเป้าหมาย พร้อมทำเครื่องหมาย `aria-invalid` และย้าย focus ไปยังช่องแรกที่ผิดตามกลไกเดิม

## การตรวจสอบและบันทึกฝั่ง Server

กฎ request ทั่วไปยังตรวจชนิดข้อมูลและรูปแบบพื้นฐาน ส่วน `SupportScoreService` ตรวจเงื่อนไขที่ขึ้นกับเกณฑ์หลังยืนยันว่า `support_criteria_id` อยู่ในรายการประเมินที่กำลังบันทึกแล้ว

Service ใช้ `SupportCriteria` ที่โหลดจากฐานข้อมูลเป็นแหล่งข้อมูลจริงสำหรับ `target_value` และปฏิเสธคะแนนระดับเกณฑ์เมื่อ:

- คะแนนไม่ใช่จำนวนเต็ม
- คะแนนต่ำกว่า `1` หรือสูงกว่า `5`
- คะแนนสูงกว่า `target_value`

การคำนวณ `weighted_score`, การเก็บประวัติ, เหตุผลการแก้ไข และหลักฐานยังทำงานเหมือนเดิมหลังคะแนนผ่าน validation

คะแนนระดับกิจกรรมต้องไม่ผ่านกฎใหม่นี้ และยังใช้ validation ของ `SupportActivityEntryService` ตามเดิม

## ข้อมูลเดิม

ไม่มี migration เพื่อแก้คะแนนที่บันทึกไว้ก่อนหน้า หน้าจออ่านอย่างเดียวและรายงานยังแสดงข้อมูลเดิมได้

เมื่อผู้ใช้เปิดรายการที่มีคะแนนระดับเกณฑ์ผิดกติกาใหม่แล้วพยายามบันทึก ระบบจะปฏิเสธ request และให้แก้คะแนนจนผ่านเงื่อนไข ข้อมูลเดิมจะไม่ถูกปรับลดโดยอัตโนมัติ

## การทดสอบ

พัฒนาด้วย TDD และเพิ่ม regression tests อย่างน้อยดังนี้:

- Blade แสดง `min="1"`, `step="1"`, `max` ตามเป้าหมาย และข้อความกำกับที่ระบุค่าเป้าหมาย
- Browser ยอมรับ `1` และคะแนนจำนวนเต็มที่เท่ากับเป้าหมาย
- Browser ปฏิเสธ `0`, `6`, ทศนิยม และค่าที่ไม่เกิน `5` แต่เกินเป้าหมาย
- Server ยอมรับคะแนนจำนวนเต็มในช่วงและไม่เกินเป้าหมาย
- Server ปฏิเสธ `0`, `6`, ทศนิยม และคะแนนที่เกินเป้าหมาย
- คะแนนรายกิจกรรมยังรับค่าตามช่วง `0–100` และทศนิยมสองตำแหน่ง
- การคำนวณคะแนนถ่วงน้ำหนักและชุดทดสอบคะแนนสายสนับสนุนเดิมยังผ่าน

## เกณฑ์ยอมรับ

ผู้ใช้กรอกคะแนนระดับเกณฑ์ได้เฉพาะจำนวนเต็ม `1–5` ที่ไม่เกินระดับค่าเป้าหมาย เห็นข้อจำกัดใต้ช่องอย่างชัดเจน และได้รับข้อความแจ้งที่สัมพันธ์กับเกณฑ์เมื่อกรอกผิด ข้อจำกัดเดียวกันถูกบังคับใช้ฝั่ง Server ขณะที่คะแนนรายกิจกรรมและ workflow อื่นไม่เปลี่ยนแปลง
