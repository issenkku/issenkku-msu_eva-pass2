# จำกัดคะแนนที่ได้ของเกณฑ์สายสนับสนุน

## เป้าหมาย

จำกัดช่อง `ค่าคะแนนที่ได้` ทั้งระดับเกณฑ์และระดับกิจกรรม/โครงการให้รับเฉพาะจำนวนเต็ม `1`, `2`, `3`, `4` หรือ `5` และค่าที่กรอกต้องไม่เกิน `ระดับค่าเป้าหมาย` ของเกณฑ์นั้น

ระบบต้องแจ้งข้อผิดพลาดทันทีใน Browser ปิดปุ่มบันทึกขณะมีคะแนนผิด และตรวจซ้ำใน Server เพื่อป้องกัน request ที่ข้ามข้อจำกัดหน้าเว็บ

## ขอบเขต

กติกาใหม่ใช้กับคะแนนสองตำแหน่ง:

- `support_list[*][achieved_score]` — คะแนนระดับเกณฑ์
- `support_list[*][activity_entries][*][achieved_score]` — คะแนนระดับกิจกรรม/โครงการ

คะแนนระดับเกณฑ์ยังคง nullable ระหว่างการแก้ไขตาม workflow ปัจจุบัน คะแนนระดับกิจกรรม/โครงการยังคง required เมื่อเกณฑ์เปิด `allow_evaluatee_weight`

น้ำหนักระดับกิจกรรม/โครงการไม่เปลี่ยนกติกา ยังคงมากกว่า `0` ไม่เกิน `100` และมีทศนิยมไม่เกินสองตำแหน่ง

## กติกาคะแนน

คะแนนที่ไม่ว่างทั้งสองตำแหน่งต้องผ่านทุกเงื่อนไขต่อไปนี้:

- เป็นจำนวนเต็ม
- มีค่าตั้งแต่ `1` ถึง `5`
- ไม่เกิน `support_criterias.target_value` ของเกณฑ์แม่

เพดานของแต่ละช่องคือค่าต่ำสุดระหว่าง `5` กับ `target_value` ตัวอย่างเช่น เกณฑ์ที่มีเป้าหมาย `3.50` จะรับจำนวนเต็มได้เฉพาะ `1`, `2` หรือ `3`

หากข้อมูลเดิมมี `target_value` ต่ำกว่า `1` จะไม่มีคะแนนที่ไม่ว่างซึ่งผ่านกติกา คะแนนระดับเกณฑ์ยังปล่อยว่างได้ แต่คะแนนระดับกิจกรรมที่ required จะบันทึกไม่ได้จนกว่า Admin จะแก้ระดับค่าเป้าหมายให้ไม่น้อยกว่า `1`

ระบบต้องคงค่าที่ผิดไว้ตามที่ผู้ใช้พิมพ์ เช่น `7` ต้องยังแสดงเป็น `7` ห้ามปรับลดเป็น `5` อัตโนมัติ

## หน้าจอและการแจ้งข้อผิดพลาด

ช่องคะแนนทั้งระดับเกณฑ์และระดับกิจกรรมใช้ `type="number"`, `min="1"`, `step="1"` และ `max` เท่ากับเพดานของเกณฑ์ พร้อมส่ง `target_value` ให้ JavaScript ผ่าน data attribute

ใต้ช่องคะแนนทุกช่องแสดงคำแนะนำตลอดเวลา:

> กรอกเฉพาะจำนวนเต็มตั้งแต่ 1–5 และต้องไม่เกินระดับค่าเป้าหมาย 4

JavaScript ตรวจทุกครั้งที่ค่า input เปลี่ยน หากค่าไม่เป็นจำนวนเต็ม อยู่นอกช่วง `1–5` หรือเกินเป้าหมาย:

- คงค่าที่ผู้ใช้พิมพ์ไว้
- เพิ่มกรอบและข้อความสีแดง
- ตั้ง `aria-invalid="true"`
- ผูกข้อความกับ input ผ่าน `aria-describedby`
- ปิดปุ่ม `บันทึก` ของ Modal

เมื่อทุกช่องในรายการกลับมาถูกต้อง ให้ล้างสถานะผิดและเปิดปุ่มบันทึกอีกครั้ง การตรวจเดิมตอนกดบันทึกยังคงอยู่เป็นชั้นป้องกันสำรองและย้าย focus ไปยังช่องแรกที่ผิดหากจำเป็น

## การตรวจสอบและบันทึกฝั่ง Server

`SupportScoreRules` ตรวจรูปแบบพื้นฐานของคะแนนทั้งสองตำแหน่งเป็น nullable integer ช่วง `1–5`

`SupportScoreService` ใช้ `SupportCriteria` ที่โหลดจากฐานข้อมูลเป็นแหล่งข้อมูลจริงสำหรับ `target_value` และตรวจคะแนนระดับเกณฑ์หลังยืนยันว่า `support_criteria_id` อยู่ในรายการประเมินที่กำลังบันทึก

`SupportActivityEntryService` ใช้ `SupportCriteria` ตัวเดียวกันตรวจคะแนนระดับกิจกรรม/โครงการก่อนคำนวณและบันทึก หากคะแนนสูงกว่า `target_value` ให้คืน `ValidationException` ที่ field path ของ activity entry นั้น

การคำนวณ `weighted_score`, การเก็บประวัติ, เหตุผลการแก้ไข และหลักฐานยังทำงานเหมือนเดิมหลังคะแนนผ่าน validation

## ข้อมูลเดิม

ไม่มี migration เพื่อแก้คะแนนที่บันทึกไว้ก่อนหน้า หน้าจออ่านอย่างเดียวและรายงานยังแสดงข้อมูลเดิมได้

เมื่อผู้ใช้เปิดรายการที่มีคะแนนผิดกติกาแล้วพยายามแก้ไขหรือบันทึก ระบบจะแสดงสถานะผิดและปฏิเสธ request จนกว่าคะแนนจะผ่านเงื่อนไข ข้อมูลเดิมจะไม่ถูกปรับลดโดยอัตโนมัติ

## การทดสอบ

พัฒนาด้วย TDD และเพิ่ม regression tests อย่างน้อยดังนี้:

- Blade แสดง `min="1"`, `step="1"`, `max` ตามเป้าหมาย, target data และคำแนะนำใต้ช่องคะแนนทั้งสองตำแหน่ง
- Browser ยอมรับ `1` และคะแนนจำนวนเต็มที่เท่ากับเป้าหมาย
- Browser คงค่า `7` ไว้ แต่ตั้งกรอบแดงและปิดปุ่มบันทึก
- Browser ปฏิเสธ `0`, `6`, ทศนิยม และค่าที่ไม่เกิน `5` แต่เกินเป้าหมาย
- Browser ล้างสถานะผิดและเปิดปุ่มบันทึกเมื่อแก้ค่าถูกต้อง
- Server ยอมรับคะแนนทั้งสองตำแหน่งเมื่อเป็นจำนวนเต็มในช่วงและไม่เกินเป้าหมาย
- Server ปฏิเสธ `0`, `6`, ทศนิยม และคะแนนที่เกินเป้าหมายทั้งสองตำแหน่ง
- น้ำหนักระดับกิจกรรมยังรับช่วง `(0, 100]` และทศนิยมสองตำแหน่ง
- การคำนวณคะแนนถ่วงน้ำหนัก ประวัติ เหตุผล และหลักฐานเดิมยังผ่าน

## เกณฑ์ยอมรับ

ผู้ใช้เห็นคำแนะนำ `กรอกเฉพาะจำนวนเต็มตั้งแต่ 1–5` ใต้คะแนนทุกช่อง เมื่อกรอกค่าผิด ระบบคงค่าที่พิมพ์ไว้ แสดงกรอบและข้อความสีแดง ปิดปุ่มบันทึก และ Server ปฏิเสธ request เดียวกัน คะแนนทั้งระดับเกณฑ์และระดับกิจกรรมต้องไม่เกินระดับค่าเป้าหมาย ขณะที่กติกาน้ำหนักและ workflow อื่นไม่เปลี่ยนแปลง
