# เกณฑ์สายสนับสนุนที่ผู้ถูกประเมินกรอกข้อมูลรายโครงการ

วันที่: 25 กรกฎาคม 2569

## เป้าหมาย

รองรับเกณฑ์สายสนับสนุนบางรายการที่ให้ผู้ถูกประเมินเพิ่มโครงการหลายรายการและกรอกกิจกรรม ตัวชี้วัด น้ำหนัก และคะแนนที่ได้เป็นรายโครงการ โดยยังใช้ Modal และการแบ่งกลุ่มตามข้อระดับที่ของระบบปัจจุบัน

ระบบต้องคำนวณคะแนนถ่วงน้ำหนักทันที ไม่มีขั้นอนุมัติก่อนนำคะแนนไปใช้ น้ำหนักของแต่ละโครงการเป็นอิสระ และคะแนนสุดท้ายของรายการประเมินต้องไม่เกิน `evaluation_lists.sum_score`

## ขอบเขต

งานนี้ครอบคลุม:

- การตั้งค่าสิทธิ์กรอกข้อมูลรายช่องใน Template ของ Admin
- การเพิ่มช่องตัวชี้วัด น้ำหนัก คะแนนที่ได้ และคะแนนถ่วงน้ำหนักในแต่ละโครงการ
- การบันทึกและแก้ไขหลายโครงการภายใต้ข้อระดับที่เดิม
- การคำนวณคะแนนถ่วงน้ำหนักรายโครงการและคะแนนรวมของรายการประเมิน
- Validation ฝั่ง Browser และ Server
- ประวัติการแก้ไขโดย Reviewer
- การแสดงผลในหน้าสรุป Dashboard หน้าต่างยืนยันส่ง และ Export
- การรักษาพฤติกรรมของเกณฑ์เดิมที่ไม่ได้เปิดความสามารถใหม่

งานนี้ไม่เพิ่มขั้นตอนอนุมัติน้ำหนักหรือตัวชี้วัด และไม่บังคับให้ผลรวมน้ำหนักเท่ากับ 100 หรือเท่ากับคะแนนรวมของรายการประเมิน

## คำศัพท์และเจ้าของข้อมูล

- **Template เกณฑ์สายสนับสนุน** คือ `support_criterias` ที่ Admin กำหนดและใช้ร่วมกันใน Criteria Version
- **โครงการ** คือ `support_activity_entries` ที่ผูกกับรายงานหนึ่งฉบับและผู้ถูกประเมินกรอกภายใต้เกณฑ์สายสนับสนุน
- **คะแนนที่คำนวณได้** คือผลรวมคะแนนถ่วงน้ำหนักก่อนจำกัดด้วยคะแนนรวม
- **คะแนนสุดท้ายของรายการประเมิน** คือคะแนนรวมของเกณฑ์ทุกประเภทภายในรายการ หลังจำกัดไม่ให้เกิน `evaluation_lists.sum_score`

ข้อมูลที่ผู้ถูกประเมินกรอกต้องอยู่ในโครงการของรายงาน ไม่เขียนทับค่าต้นฉบับใน Template

## การตั้งค่า Template

ใช้ `support_criterias.allow_activity_entries` เดิมเพื่ออนุญาตให้ผู้ถูกประเมินเพิ่มหลายโครงการ และเพิ่ม boolean สองค่า:

- `allow_evaluatee_indicator` — อนุญาตให้กรอกตัวชี้วัดในแต่ละโครงการ
- `allow_evaluatee_weight` — อนุญาตให้กรอกน้ำหนักในแต่ละโครงการ

ค่าเริ่มต้นของทั้งสอง field เป็น `false` เพื่อรักษาพฤติกรรมของเกณฑ์เดิม

ข้อกำหนดของการตั้งค่า:

- เปิด `allow_evaluatee_indicator` หรือ `allow_evaluatee_weight` ได้เฉพาะเมื่อเปิด `allow_activity_entries`
- เมื่อปิด `allow_activity_entries` หน้า Admin ต้องปิดและล้างสองตัวเลือกใหม่ก่อนส่ง payload
- API ฝั่ง Server ต้องตรวจ dependency นี้ซ้ำและไม่ยอมรับสถานะที่ขัดแย้ง
- การ Create, Edit และ Clone Criteria Version ต้องรับส่งและคัดลอก flags ใหม่
- การ Clone คัดลอกเฉพาะ Template และ flags ไม่คัดลอกข้อมูลโครงการของรายงาน

## รูปแบบหน้าจอ

### หน้า Admin

ในแต่ละเกณฑ์สายสนับสนุน เพิ่มตัวเลือกต่อจาก “อนุญาตให้ผู้ถูกประเมินเพิ่มกิจกรรม/โครงการ”:

- อนุญาตให้ผู้ถูกประเมินกรอกตัวชี้วัด
- อนุญาตให้ผู้ถูกประเมินกรอกน้ำหนัก

หน้า Admin ยังคงใช้ช่องกิจกรรม ตัวชี้วัด ระดับค่าเป้าหมาย น้ำหนัก และตัวเลือกอื่นของ Template เหมือนเดิมสำหรับเกณฑ์ที่ไม่เปิดความสามารถใหม่

### Modal ของผู้ถูกประเมิน

คง Modal เดิม ได้แก่:

- หัวข้อเรื่อง
- การแบ่งกลุ่มตามข้อระดับที่
- ปุ่ม “เพิ่มโครงการในข้อระดับที่”
- รายการหลักฐานของแต่ละโครงการ

เมื่อเพิ่มโครงการ ให้แสดง field ตามสิทธิ์ของเกณฑ์:

1. กิจกรรม/โครงการ/งาน — Rich Text เดิม
2. ตัวชี้วัด/เกณฑ์การประเมิน — Rich Text เมื่อเปิด `allow_evaluatee_indicator`
3. น้ำหนัก — ตัวเลขเมื่อเปิด `allow_evaluatee_weight`
4. ค่าคะแนนที่ได้ — ตัวเลขรายโครงการเมื่อเปิด `allow_evaluatee_weight`
5. คะแนนถ่วงน้ำหนัก — ค่าอ่านอย่างเดียวที่ระบบคำนวณ
6. หลักฐาน — ใช้พฤติกรรมเดิม

เมื่อเปิด `allow_evaluatee_weight` ต้องซ่อนช่อง “ค่าคะแนนที่ได้” และ “คะแนนถ่วงน้ำหนัก” ระดับเกณฑ์ที่อยู่ด้านล่างรายการโครงการ เพื่อไม่ให้มีแหล่งคะแนนสองชุด

เกณฑ์ที่เปิดเพียง `allow_evaluatee_indicator` แต่ไม่เปิด `allow_evaluatee_weight` ยังคงใช้คะแนนและน้ำหนักระดับเกณฑ์ตามพฤติกรรมเดิม

## แบบข้อมูล

เพิ่มคอลัมน์ใน `support_activity_entries`:

- `indicator` — text nullable
- `weight` — decimal nullable
- `achieved_score` — decimal nullable
- `weighted_score` — decimal nullable

คอลัมน์เป็น nullable เพื่อรองรับข้อมูลเดิมและเกณฑ์ที่ไม่ได้เปิดความสามารถใหม่

ขยายข้อมูลประวัติของโครงการให้เก็บค่าเดิมและค่าใหม่ของ:

- กิจกรรม
- ตัวชี้วัด
- น้ำหนัก
- คะแนนที่ได้
- คะแนนถ่วงน้ำหนัก

ประวัติต้องเก็บผู้แก้ไข บทบาท เหตุผล และเวลาตามกลไกเดิม การเลือกชนิดและ precision ของ decimal ให้สอดคล้องกับ `support_criterias.weight`, `support_scores.achieved_score` และ `support_scores.weighted_score` ที่ใช้อยู่

## Payload และ Read Model

แต่ละรายการใน `support_list.*.activity_entries` เพิ่ม:

- `indicator`
- `weight`
- `achieved_score`

Browser ไม่ต้องส่ง `weighted_score` หากส่งมา Server ต้องไม่ใช้ค่านั้นในการบันทึก

Read Model ของเกณฑ์สายสนับสนุนต้องคืน field ใหม่ flags ใหม่ และประวัติ โดยโหลดรายการเป็นชุดตาม `report_id` และ `support_criteria_id` ห้ามเพิ่ม query ต่อโครงการ

ทุกโครงการต้องคง `id`, `support_criteria_id` และ `support_indicator_item_id` เพื่อให้ Server ตรวจว่าเป็นข้อมูลของรายงาน เกณฑ์ และข้อระดับที่เดียวกัน

## การคำนวณคะแนน

เมื่อเปิด `allow_evaluatee_weight` ให้คำนวณรายโครงการ:

```text
คะแนนถ่วงน้ำหนัก = น้ำหนัก × คะแนนที่ได้ ÷ 100
```

หลักการคำนวณ:

- Browser คำนวณเพื่อ preview ทันทีเมื่อแก้น้ำหนักหรือคะแนนที่ได้
- Server คำนวณซ้ำและเป็นแหล่งความจริง
- ปัดคะแนนถ่วงน้ำหนักเป็นทศนิยมสองตำแหน่งด้วยหลักการเดียวกับคะแนนสายสนับสนุนเดิม
- คะแนนดิบของเกณฑ์คือผลรวม `weighted_score` ของโครงการในเกณฑ์นั้น
- เกณฑ์เดิมที่ไม่เปิด `allow_evaluatee_weight` ใช้ `support_scores` ระดับเกณฑ์เหมือนเดิม
- คะแนนดิบสายสนับสนุนของรายการประเมินรวมคะแนนจากทั้งเกณฑ์เดิมและเกณฑ์แบบรายโครงการ

รายการประเมินหนึ่งรายการเปิดเกณฑ์ปริมาณ คุณภาพ และสายสนับสนุนพร้อมกันได้ การรวมคะแนนต้องเกิดในขอบเขตของแต่ละ `evaluation_list`:

```text
คะแนนดิบของรายการ =
    คะแนนปริมาณในรายการ
  + คะแนนคุณภาพในรายการ
  + คะแนนสายสนับสนุนในรายการ

คะแนนสุดท้ายของรายการ =
  min(คะแนนดิบของรายการ, evaluation_list.sum_score)
```

คะแนนรวมรายงานคือผลรวมคะแนนสุดท้ายของแต่ละรายการประเมิน ห้าม cap คะแนนรวมสายสนับสนุนแยกต่างหากจนทำให้ข้ามขอบเขต `evaluation_list`

ระบบสามารถแสดงคะแนนดิบเพื่ออธิบายการคำนวณ เช่น คำนวณได้ 86 แต่คะแนนสุดท้ายเป็น 75

## Validation และความปลอดภัย

### กิจกรรมและตัวชี้วัด

- ตรวจ Rich Text หลังแปลงเป็น plain text
- ไม่รับค่าที่ว่างจริง เช่น `<p><br></p>`, whitespace หรือ markup ที่ไม่มีข้อความ
- sanitize ด้วยกลไก `SafeHtml` เดิม
- `indicator` เป็น required เฉพาะเมื่อ `allow_evaluatee_indicator` เป็น true
- เมื่อ flag เป็น false Server ต้องปฏิเสธค่าที่พยายามส่งเข้ามาแทนการบันทึกข้อมูลที่ไม่มีสิทธิ์

### น้ำหนักและคะแนน

- `weight` เป็น required เมื่อ `allow_evaluatee_weight` เป็น true
- น้ำหนักต้องมากกว่า 0 และไม่เกิน 100
- `achieved_score` เป็น required เมื่อ `allow_evaluatee_weight` เป็น true
- คะแนนที่ได้ต้องตั้งแต่ 0 ถึง 100
- รองรับทศนิยมไม่เกินสองตำแหน่ง
- ไม่บังคับผลรวมน้ำหนักของโครงการ
- Server คำนวณ `weighted_score` เองทุกครั้ง

### ความสัมพันธ์ของข้อมูล

Server ต้องตรวจว่า:

- เกณฑ์อยู่ใน Criteria Version ของรายงาน
- โครงการเป็นของรายงานและเกณฑ์ที่ส่งมา
- ข้อระดับที่เป็นของเกณฑ์เดียวกัน
- ID เดิมไม่ถูกเปลี่ยนเพื่อย้ายโครงการข้ามเกณฑ์หรือข้ามข้อระดับที่
- ผู้ใช้มีบทบาทและสิทธิ์แก้ไขตาม flow ปัจจุบัน

ข้อผิดพลาดต้องผูกกับ path ของโครงการ เช่น `support_list.{criterion}.activity_entries.{index}.weight` เพื่อแสดงใต้ field ที่ผิด และข้อมูลในโครงการอื่นต้องคงอยู่หลัง validation ล้มเหลว

## การบันทึกและประวัติ

การบันทึกโครงการ คะแนน หลักฐาน ประวัติ และคะแนนสรุปรายงานต้องอยู่ใน transaction เดียวกัน

ผู้ถูกประเมินเพิ่ม แก้ไข และลบโครงการตามสถานะที่ระบบปัจจุบันอนุญาต เมื่อบันทึกสำเร็จ คะแนนสรุปต้องอัปเดตทันทีโดยไม่มีขั้นอนุมัติเพิ่ม

Reviewer:

- แก้กิจกรรม ตัวชี้วัด น้ำหนัก หรือคะแนนที่ได้ของโครงการเดิมได้ตามสิทธิ์ปัจจุบัน
- ต้องระบุเหตุผลเมื่อค่าที่มีอยู่เปลี่ยน
- ไม่เปลี่ยน ID หรือตำแหน่งข้อระดับที่ของโครงการ
- การแก้ไขต้องคำนวณคะแนนถ่วงน้ำหนักและคะแนนสรุปใหม่

## หน้าสรุปและ Export

หน้าต่อไปนี้ต้องอ่านคะแนนจากกติกาเดียวกัน:

- Modal ของผู้ถูกประเมิน
- หน้าต่างยืนยันส่ง
- หน้าผู้ประเมิน Reviewer Manager และ Director
- Dashboard และสรุปคะแนนรายงาน
- Export รายงาน

สำหรับเกณฑ์แบบรายโครงการ ให้แสดงกิจกรรม ตัวชี้วัด น้ำหนัก คะแนนที่ได้ และคะแนนถ่วงน้ำหนักของแต่ละโครงการ รวมถึงคะแนนดิบและคะแนนสุดท้ายเมื่อเกิดการ cap

## การย้ายข้อมูลและความเข้ากันได้

- Migration เพิ่มคอลัมน์ nullable และ flags ที่มีค่าเริ่มต้น false
- ไม่ backfill ข้อมูลเก่าเป็นรายการคะแนนรายโครงการ
- เกณฑ์และรายงานเดิมทำงานผ่าน `support_scores` เหมือนเดิม
- การเปิดความสามารถใหม่ใน Template มีผลกับการกรอกข้อมูลของรายงานที่อ้าง Criteria Version นั้นตามกติกาการแก้ Template ปัจจุบัน
- ห้ามลบหรือย้ายข้อมูลคะแนนเดิมอัตโนมัติเมื่อเปิด flag ในเกณฑ์ที่มีรายงานเริ่มกรอกแล้ว การเปลี่ยนโหมดดังกล่าวต้องถูกป้องกันหรือจัดการด้วย validation ตามสถานะใช้งานของ Criteria Version

## การทดสอบ

### Template

- Create, Edit, Read และ Clone รักษา flags ใหม่
- ปฏิเสธ flags ใหม่เมื่อ `allow_activity_entries` เป็น false
- เกณฑ์เดิมมี flags เป็น false และหน้าจอไม่เปลี่ยน

### Modal และ JavaScript

- เพิ่ม แก้ไข และลบหลายโครงการในแต่ละข้อระดับที่
- แสดง field ตาม flags
- คำนวณ preview เมื่อแก้น้ำหนักหรือคะแนน
- ซ่อนคะแนนระดับเกณฑ์เมื่อใช้คะแนนรายโครงการ
- Validation ผิดพลาดไม่ล้างค่าของโครงการอื่น

### Service และความปลอดภัย

- คำนวณ `weighted_score` ถูกต้องและไม่เชื่อค่าจาก Browser
- รับน้ำหนักทศนิยมที่อยู่ในช่วง
- ปฏิเสธน้ำหนัก 0 ติดลบ หรือเกิน 100
- ปฏิเสธคะแนนต่ำกว่า 0 หรือเกิน 100
- ปฏิเสธ Rich Text ว่าง
- ปฏิเสธโครงการ เกณฑ์ หรือข้อระดับที่ของรายงานอื่น
- บันทึกข้อมูล คะแนน หลักฐาน และประวัติแบบ atomic

### คะแนนรวม

- น้ำหนักแต่ละโครงการไม่ต้องรวมเป็น 100
- รวมคะแนนเกณฑ์เดิมและคะแนนรายโครงการได้
- เปิดเกณฑ์ปริมาณ คุณภาพ และสายสนับสนุนพร้อมกันได้
- คะแนนดิบต่ำกว่า `sum_score` ไม่ถูกเปลี่ยน
- คะแนนดิบเกิน 75 ในรายการที่มี `sum_score = 75` ให้คะแนนสุดท้าย 75
- คะแนนรวมรายงานเท่ากับผลรวมคะแนนสุดท้ายของรายการประเมิน

### การแสดงผล

- Reviewer เห็นและแก้ field รายโครงการพร้อมเหตุผลได้
- ประวัติแสดงค่าเดิมและค่าใหม่ครบ
- หน้าต่างยืนยันส่ง Dashboard และ Export แสดงคะแนนตรงกับ Server
- Export แสดงกิจกรรม ตัวชี้วัด น้ำหนัก คะแนน และคะแนนถ่วงน้ำหนักรายโครงการ

## เกณฑ์ยอมรับ

Admin สามารถเปิดสิทธิ์ให้ผู้ถูกประเมินกรอกตัวชี้วัดและน้ำหนักเป็นรายเกณฑ์ได้ ผู้ถูกประเมินเพิ่มหลายโครงการภายใต้ข้อระดับที่เดิม กรอกข้อมูลและเห็นคะแนนถ่วงน้ำหนักทันที ระบบบันทึกและคำนวณซ้ำอย่างปลอดภัยโดยไม่บังคับผลรวมน้ำหนัก และคะแนนสุดท้ายของแต่ละรายการประเมินไม่เกิน `sum_score` ขณะที่เกณฑ์และรายงานเดิมยังทำงานเหมือนเดิม
