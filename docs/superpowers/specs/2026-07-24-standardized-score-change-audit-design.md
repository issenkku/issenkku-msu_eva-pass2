# Standardized Score Change Audit Design

**Date:** 2026-07-24
**Status:** Approved

## Goal

ทำให้คะแนนด้านปริมาณ คะแนนด้านคุณภาพ และคะแนนสายสนับสนุนใช้มาตรฐานเดียวกันสำหรับเหตุผลและประวัติการแก้ไข โดยคงวิธีกรอกคะแนนที่เหมาะกับแต่ละประเภทไว้ตามเดิม

มาตรฐานร่วมต้องครอบคลุมการเพิ่มคะแนนจากค่าว่าง การเปลี่ยนคะแนนเดิม และการลบคะแนนเดิมออก

## Scope

### In scope

- กติกากลางสำหรับตรวจว่าคะแนนเปลี่ยนหรือไม่
- การบังคับเหตุผลตามบทบาทผู้ใช้งาน
- เหตุผลแยกต่อรายการคะแนนที่เปลี่ยน
- ประวัติคะแนนด้านปริมาณที่รองรับการเพิ่ม แก้ และลบ
- ประวัติคะแนนด้านคุณภาพแบบมีโครงสร้าง
- การนำกติกากลางไปใช้กับคะแนนสายสนับสนุน
- รูปแบบการแสดงประวัติที่สอดคล้องกัน
- คอลัมน์และ Modal สำหรับเปิดดูประวัติคะแนนในตารางสายสนับสนุน
- Server-side validation, transaction rollback และ automated tests

### Out of scope

- การย้ายประวัติเดิมไปรวมไว้ในตารางเดียว
- การเปลี่ยนวิธีกรอกคะแนนของแต่ละประเภท
- การเลือกชนิดเกณฑ์จาก `personnel_type`
- การแก้ความไม่ตรงกันระหว่างคะแนนผลสัมฤทธิ์สายสนับสนุนบนหน้าจอกับ Backend เมื่อผลรวมคะแนนถ่วงน้ำหนักเกิน 100
- การ backfill เหตุผลหรือประวัติย้อนหลัง

## Roles and Policy

### ผู้รับการประเมิน

- แก้คะแนนได้เฉพาะสถานะที่ Flow เดิมอนุญาต
- ไม่บังคับเหตุผลระหว่าง Assigned/Draft
- เก็บประวัติเมื่อมีการเพิ่ม แก้ หรือลบคะแนน

### ผู้ตรวจ

คำว่า “ผู้ตรวจ” ในเอกสารนี้ครอบคลุม:

- ผู้ประเมิน
- กรรมการ
- ผู้บริหาร

ผู้ตรวจต้องระบุเหตุผลแยกต่อรายการทุกครั้งที่:

- เพิ่มคะแนนจากเดิมที่ไม่มีคะแนน
- เปลี่ยนคะแนนเดิม
- ลบคะแนนเดิมหรือยกเลิกเกณฑ์ที่เคยเลือก

ข้อความว่างหรือมีเฉพาะ whitespace ถือว่าไม่ได้ระบุเหตุผล เหตุผลมีความยาวสูงสุด 2,000 ตัวอักษร

คำขอที่ไม่มีการเปลี่ยนแปลงจะไม่สร้างประวัติ แม้ผู้ใช้ส่งเหตุผลมาด้วย

## Recommended Architecture

ใช้มาตรฐานพฤติกรรมร่วม แต่คงตารางประวัติแยกตามประเภทคะแนน

แนวทางนี้รักษาความเข้ากันได้กับข้อมูลเดิม ลดขอบเขต migration และเปิดให้แต่ละประเภทเก็บข้อมูลเฉพาะของตนเองได้ โดยไม่ทำให้กติกาการตรวจการเปลี่ยนแปลงแตกต่างกันอีก

### Shared change policy

เพิ่มหน่วยงานกลางที่รับผิดชอบ:

- normalize ค่าก่อนและหลังสำหรับการเปรียบเทียบ
- ตรวจจับการเปลี่ยน `null → value`, `value → value` และ `value → null`
- ตัดสินว่าบทบาทปัจจุบันต้องระบุเหตุผลหรือไม่
- validate และ normalize เหตุผล
- คืนผลการเปรียบเทียบในรูปแบบที่ recorder ของแต่ละประเภทนำไปใช้ได้

กติกากลางไม่บันทึกฐานข้อมูลเอง การบันทึกประวัติยังเป็นหน้าที่ของ recorder/service ของคะแนนแต่ละประเภท เพื่อให้ขอบเขตความรับผิดชอบชัดเจน

## Data Model

### Quantity score history

เพิ่มคอลัมน์ `reason` แบบ nullable text ใน `quantity_score_histories`

ปรับ recorder ให้บันทึก:

- `previous_score_c`
- `new_score_c`
- `previous_description`
- `new_description`
- `reason`
- `modifier_user_id`
- `modifier_role`
- timestamp

Recorder ต้องไม่ข้ามกรณีที่ไม่มี row เดิมอีกต่อไป แต่ต้องรองรับทั้งการเพิ่มและการลบคะแนน

ค่า D ยังคำนวณจาก A, B และ C ตามเดิม ประวัติหลักของการเปลี่ยนแปลงใช้ค่า C เป็น input ที่ผู้ใช้แก้ ส่วนหน้าจอสามารถแสดงค่า D ที่คำนวณจาก snapshot เดิมและใหม่ได้เมื่อข้อมูล A/B พร้อม

### Quality score history

เพิ่มตาราง `quality_score_histories` ประกอบด้วย:

- `report_id`
- `quality_sub_criteria_id`
- `previous_score` nullable
- `new_score` nullable
- `reason` nullable text
- `modifier_user_id` nullable
- `modifier_role` nullable
- timestamps

ความหมายของค่า `null` คือไม่ได้เลือกเกณฑ์หรือไม่มีคะแนน:

- `null → value` คือเลือกหรือเพิ่มคะแนน
- `value → null` คือยกเลิกหรือลบคะแนน
- `value A → value B` คือเปลี่ยนคะแนน

### Support score history

คง `support_scores` และ `support_score_histories` เดิม รวมถึงข้อมูล:

- achieved score เดิมและใหม่
- weighted score เดิมและใหม่
- เหตุผล
- ผู้แก้และบทบาท
- timestamp

ปรับเฉพาะการตรวจจับการเปลี่ยนและการบังคับเหตุผลให้ใช้กติกากลาง

## Request and Persistence Flow

ทุก controller ที่บันทึกคะแนนต้องทำงานตามลำดับต่อไปนี้ภายใน transaction เดียว:

1. โหลด snapshot คะแนนเดิมของทั้งสามประเภท
2. validate payload และตรวจว่า criteria IDs เป็นของรายงาน/criteria version ปัจจุบัน
3. สร้าง snapshot คะแนนใหม่จาก payload ก่อนลบหรือเขียนข้อมูลเดิม
4. เปรียบเทียบ old/new เป็นรายรายการด้วยกติกากลาง
5. validate เหตุผลสำหรับรายการที่เปลี่ยนตามบทบาท
6. บันทึกคะแนน หลักฐาน และประวัติ
7. บันทึก comment และเปลี่ยนสถานะรายงานตาม Flow เดิม
8. commit เมื่อทุกขั้นตอนสำเร็จ

หาก validation หรือการบันทึกส่วนใดล้มเหลว ต้อง rollback คะแนน ประวัติ หลักฐาน comment และสถานะรายงานทั้งหมดในคำขอนั้น

## User Interface

### Quantity

- คงการแก้ค่า C แบบ inline
- คงการคำนวณ D แบบเดิม
- เพิ่มช่อง “เหตุผลที่แก้ไขคะแนน” ต่อรายการ
- แสดงช่องเหตุผลแก่ผู้ตรวจในโหมดแก้ไข
- JavaScript บังคับเหตุผลเฉพาะเมื่อค่าก่อนและหลังต่างกัน แต่ Server เป็นแหล่งตัดสินสุดท้าย

### Quality

- คง Checkbox และ hidden score input ตามเดิม
- เพิ่มช่องเหตุผลที่ผูกกับ quality sub-criterion แต่ละรายการ
- การเลือกใหม่ ยกเลิก หรือเปลี่ยนคะแนนถือเป็นการเปลี่ยนแปลง
- เมื่อ validation ผิด ให้เปิดส่วนของเกณฑ์ที่เกี่ยวข้องและ focus ช่องเหตุผลแรก

### Support

- คง Modal และการจัดการหลักฐานเดิม
- คงข้อจำกัดว่าผู้รับการประเมินแก้หลักฐานได้ ส่วนผู้ตรวจอ่านหลักฐานอย่างเดียว
- ใช้ข้อความ validation และกติกาการบังคับเหตุผลร่วมกับคะแนนประเภทอื่น

#### Support history column and modal

เพิ่มคอลัมน์ “ประวัติการแก้ไข” ในตารางเกณฑ์สายสนับสนุน โดยวางระหว่างคอลัมน์ “คะแนนถ่วงน้ำหนัก” และ “หลักฐาน”

- เมื่อรายการมีประวัติ แสดงปุ่ม Badge เป็นจำนวนครั้ง เช่น “3 ครั้ง”
- เมื่อไม่มีประวัติ แสดง “–” และไม่สร้างปุ่ม
- แสดงคอลัมน์นี้ทั้งโหมดแก้ไขและโหมดอ่านอย่างเดียว
- การกด Badge เปิด Modal ประวัติของเกณฑ์รายการนั้น
- Modal แสดงคะแนนเดิม → คะแนนใหม่ คะแนนถ่วงน้ำหนักเดิม → ใหม่ เหตุผล ผู้แก้ บทบาท และวันเวลา
- Modal ต้องรองรับปุ่มปิด, ปุ่ม Escape, focus trap และคืน focus ไปยัง Badge ที่เปิด Modal
- บน Mobile แสดง “ประวัติการแก้ไข: N ครั้ง” ภายใน Card และเปิด Modal เดียวกัน
- ปรับสัดส่วนคอลัมน์กิจกรรมและตัวชี้วัดลงเล็กน้อย เพื่อคง fixed-width table และไม่เพิ่ม horizontal scroll
- ย้ายรายละเอียดประวัติเดิมออกจาก editor store ที่ซ่อนอยู่มาใช้ Modal กลาง เพื่อไม่ render ข้อมูลรายละเอียดซ้ำ

คอลัมน์นี้ใช้เฉพาะตารางเกณฑ์สายสนับสนุน คะแนนปริมาณและคะแนนคุณภาพยังแสดงประวัติในพื้นที่รายละเอียดของรายการตามรูปแบบเดิมที่กำหนดใน design นี้

### Shared history presentation

ประวัติทุกประเภทแสดงในรูปแบบเดียวกัน:

- ค่าเดิม → ค่าใหม่
- เหตุผล
- ผู้แก้
- บทบาท
- วันและเวลา

ใช้คำว่า “ไม่มีคะแนน” แทนค่า `null` เพื่อให้กรณีเพิ่มและลบคะแนนอ่านได้ชัดเจน

ในโหมดอ่านอย่างเดียว:

- ไม่แสดงช่องกรอกเหตุผล
- ไม่แสดง control สำหรับแก้คะแนน
- ยังแสดงประวัติทั้งหมดที่ผู้ใช้มีสิทธิ์ดู

## Validation and Error Handling

- ตรวจค่าคะแนนตามกติกาเดิมของแต่ละประเภท
- ปฏิเสธ criteria ID ที่ไม่อยู่ในรายงานหรือ criteria version ปัจจุบัน
- เหตุผลของผู้ตรวจต้องไม่ว่างและยาวไม่เกิน 2,000 ตัวอักษร
- คืน validation errors ด้วย path ระดับรายการ เพื่อให้หน้า UI ระบุตำแหน่งผิดได้
- หากหลายรายการผิด ให้คืนข้อผิดพลาดครบทุก path ที่ตรวจพบ
- UI เปิดส่วนที่เกี่ยวข้องและ focus รายการผิดรายการแรก
- Server-side validation เป็น authoritative แม้ JavaScript ถูกปิดหรือถูกข้าม

## Compatibility

- ประวัติคะแนนปริมาณและสายสนับสนุนเดิมยังอ่านได้
- `reason` ของประวัติปริมาณเดิมจะเป็น `null`
- ประวัติคุณภาพเริ่มสะสมหลัง deploy
- ไม่เปลี่ยนสูตรคะแนน สถานะรายงาน หรือ Assignment Flow
- ไม่เปลี่ยนรูปแบบการกรอกหลักของแต่ละประเภท

## Testing

### Shared policy tests

- ตรวจจับ `null → value`, `value → value`, `value → null`
- ไม่ถือว่าค่าตัวเลขที่เท่ากันหลัง normalize เป็นการเปลี่ยน
- ผู้รับการประเมินไม่ต้องมีเหตุผล
- ผู้ตรวจต้องมีเหตุผล
- whitespace-only reason ไม่ผ่าน
- เหตุผลเกิน 2,000 ตัวอักษรไม่ผ่าน

### Quantity tests

- เพิ่ม แก้ และลบค่า C สร้างประวัติ
- ผู้ตรวจทำทั้งสามกรณีโดยไม่มีเหตุผลไม่ได้
- ผู้รับการประเมินทำได้โดยไม่ต้องมีเหตุผล
- ไม่เปลี่ยน C/description ไม่สร้างประวัติ
- ประวัติแสดงค่าเดิม ค่าใหม่ เหตุผล ผู้แก้ บทบาท และเวลา

### Quality tests

- เลือกเกณฑ์ใหม่สร้างประวัติ
- ยกเลิกเกณฑ์สร้างประวัติ
- เปลี่ยนคะแนนสร้างประวัติ
- ผู้ตรวจต้องระบุเหตุผลในทุกกรณี
- ผู้รับการประเมินไม่ต้องระบุเหตุผล
- ไม่เปลี่ยนการเลือกหรือคะแนนไม่สร้างประวัติ

### Support regression tests

- ผู้ตรวจยังต้องระบุเหตุผลเมื่อคะแนนเปลี่ยน
- ผู้รับการประเมินยังไม่ต้องระบุเหตุผล
- เพิ่ม แก้ และลบคะแนนมีประวัติ
- หลักฐานและกิจกรรมยังคงทำงานตามเดิม

### Transaction and authorization tests

- validation failure rollback คะแนน ประวัติ หลักฐาน comment และสถานะ
- history persistence failure rollback ทั้งคำขอ
- criteria ID จากรายงานหรือ version อื่นถูกปฏิเสธ
- ผู้ใช้แก้คะแนนได้เฉพาะสถานะและบทบาทที่ Flow เดิมอนุญาต

### View and JavaScript tests

- ช่องเหตุผลแสดงเฉพาะบทบาท/โหมดที่ถูกต้อง
- โหมดอ่านอย่างเดียวไม่มี editable inputs
- ประวัติทั้งสามประเภทใช้ข้อมูลและรูปแบบเดียวกัน
- ตารางสายสนับสนุนแสดงคอลัมน์ประวัติทั้งโหมดแก้ไขและอ่านอย่างเดียว
- รายการที่มีประวัติแสดง Badge จำนวนครั้ง และรายการที่ไม่มีประวัติแสดง “–”
- Badge เปิด Modal ของเกณฑ์ที่ถูกต้องและแสดงรายละเอียดครบ
- Mobile Card แสดงจำนวนประวัติและเปิด Modal เดียวกับ Desktop
- Modal ประวัติรองรับการปิดด้วยปุ่ม Escape, focus trap และคืน focus
- ตารางยังเป็น fixed-width และไม่มี horizontal scroll
- validation เปิดส่วนที่ผิดและ focus ช่องแรก
- การแก้คะแนนเดิมยังคงทำงานตาม UI เฉพาะของแต่ละประเภท

## Acceptance Criteria

งานถือว่าสำเร็จเมื่อ:

1. คะแนนทั้งสามประเภทใช้กติกาเดียวกันในการตรวจเพิ่ม แก้ และลบ
2. ผู้ตรวจไม่สามารถบันทึกการเปลี่ยนคะแนนโดยไม่มีเหตุผลต่อรายการ
3. ผู้รับการประเมินไม่ถูกบังคับเหตุผล แต่ทุกการเปลี่ยนมีประวัติ
4. ประวัติแสดงค่าเดิม ค่าใหม่ เหตุผล ผู้แก้ บทบาท และเวลา
5. ไม่สร้างประวัติเมื่อข้อมูลไม่เปลี่ยน
6. ความล้มเหลวส่วนใดส่วนหนึ่ง rollback ทั้งคำขอ
7. วิธีกรอกคะแนนปริมาณ คุณภาพ และสนับสนุนยังคงเดิม
